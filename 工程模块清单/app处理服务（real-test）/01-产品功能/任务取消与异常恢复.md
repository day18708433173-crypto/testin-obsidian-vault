# 任务取消与异常恢复

> 本文是 [04-任务取消与异常恢复](../04-复杂功能细节/核心链路-任务取消与异常恢复.md) 的自然语言版（不含代码细节）。

## 功能是什么

任务在到达终态之前可以被终止。终止有两条路径：**用户主动取消**（含批量取消、第三方系统代取消、欠费取消）和**设备异常被动取消**（设备离线时平台自动清理）。设备异常取消的任务还有"复活"机制——设备重新上线后，这些任务会自动恢复排队，不需要用户重新提交。

## 一、用户主动取消

### 取消时平台做什么

1. 校验操作人对该项目组的权限，然后检查任务当前状态。
2. 把任务下所有未到终态的执行单元（待调度、待执行、执行中、预完成）统一置为"已取消"。
3. 对正在设备上执行的部分，额外通知设备端停止执行，并释放设备占用和测试账号。
4. 同步更新门户与测试计划侧的任务状态。

### 业务规则

- **幂等**：已经在取消中或已取消的任务，再次取消直接返回成功，不会重复处理。
- **已完成的任务不可取消**：点取消会直接返回成功（任务本来已结束）；若任务来自测试计划，会补发一次完成同步。
- **级联取消**：取消一个任务会连带取消其下所有未完成的执行单元，不能只取消一半。
- **批量取消容错**：批量取消时单个任务失败不影响其他任务，最终返回成功取消的数量。
- **多端联动取消**：多端联动任务（一个任务跨多个端）取消时，会自动联动取消所有关联端的子任务，保证整组任务一起终止。
- **第三方代取消**：外部系统（如恒生等对接方）可以通过专用接口取消任务，无需提供操作人身份，其余流程与用户取消一致。
- **欠费取消**：欠费触发的取消与用户取消走相同链路，但会单独标记原因，用于业务统计和追溯。

## 二、设备异常被动取消

### 触发方式

平台通过多层机制感知设备离线：长连接断开、心跳超时、数据库中的心跳记录过期，层层确认后判定设备异常。

### 异常时平台做什么

设备被判定离线后，该平台自动批量取消该设备上所有未到终态的任务，处理方式与用户取消一致（执行中的还会确保设备端停止、释放资源），但取消原因统一标记为**设备异常**——这个标记是后续自动恢复的凭据。取消结果会同步回门户，用户看到的任务状态与用户取消相同，但原因可区分。

> 异常处理是批量异步进行的，避免设备短时网络抖动造成误判：从离线检测到任务被取消会有数十秒级的确认窗口。

### 自动恢复

设备重新上线（重新连接、认证、心跳恢复）后，平台会把之前因"设备异常"被取消、且仍在有效期内的任务自动恢复为"待执行"，重新绑定设备并回到调度池排队，门户侧状态同步恢复。

恢复有明确边界：

- 只有**设备异常**原因取消的任务才能恢复；用户主动取消、欠费取消的任务永远不会自动恢复。
- 恢复前会再次确认设备确实在线；设备仍不在线则保持取消状态。
- 任务超过有效时间（约 5 小时）后不再恢复，防止过期任务复活。

## 两条路径对比

| 维度 | 用户主动取消 | 设备异常取消 |
|---|---|---|
| 触发方 | 用户 / 第三方系统 / 欠费 | 平台自动检测 |
| 取消范围 | 指定任务（或批量指定） | 离线设备上的全部在途任务 |
| 设备端停止 | 执行中的会通知停止 | 同样通知停止 |
| 资源释放 | 释放设备与账号 | 同样释放 |
| 可自动恢复 | 否 | 是（设备重新上线后，5 小时内） |
