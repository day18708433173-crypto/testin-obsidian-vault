# 设备匹配与下发

> 本文是 [04-核心链路-设备匹配与下发](../04-复杂功能细节/核心链路-设备匹配与下发.md) 的自然语言版（不含代码细节）。

## 功能是什么

- 设备匹配与下发回答的问题是："**这台刚报到的设备，现在有没有适合它跑的任务？有就交给它。**"它是"任务"和"设备"之间的撮合环节：设备控制中心收到上位机心跳后，把设备信息转给任务调度服务寻找待执行任务，找到后经长连接把任务下发给上位机执行。
- 整个过程对上游（提测用户）透明：用户只需提交任务并指明对设备的要求，剩下的"哪台设备什么时候领走任务"由匹配机制自动完成。

## 触发时机

- 匹配由**设备心跳驱动**：上位机每次心跳都会汇报所挂设备的状态，其中"空闲且已授权"的设备会被推进匹配流程。设备不心跳，就没有匹配机会。
- 匹配按资源类型分三条独立的线：**App 真机**、**Web 浏览器**、**PC 客户端** 各自排队、各自匹配，互不挤占。

## 匹配规则

任务在创建时可以声明对执行设备的要求，匹配时按任务类型套用相应规则：

| 任务类型 | 可声明的要求 | 匹配方式 |
|---|---|---|
| App | 指定具体设备 | 只有名单内的设备能领到该任务 |
| App | 手机型号 | 型号相符的设备才可匹配 |
| App | 系统版本（Android / iOS） | 系统版本相符的设备才可匹配 |
| App | 品牌 + 型号 + 系统 + 分辨率全部条件 | 全部满足才匹配（最严格） |
| Web | 浏览器类型与版本 | 上位机上相符的浏览器才可匹配 |
| PC | 客户端类型 | 相符的 PC 客户端才可匹配 |

匹配前还会做一轮快速初筛（按型号、系统、状态先过滤掉明显不符的候选任务），只在候选集里做精细匹配，保证心跳高峰时也能快速响应。

## 约束与保护机制

- **设备必须空闲且未被占用**：正在跑别的任务或被占用的设备不会参与匹配，匹配请求会直接得到"设备已占用"的结果。
- **一台设备与一个任务只配对一次**：匹配成功会留下配对记录，防止同一任务被重复下发给同一台设备。
- **一个任务不会被多台设备同时抢走**：匹配过程有并发保护，即使多台设备同时心跳，同一个任务也只会成交给其中一台。
- **匹配成功即占位**：任务一旦匹配成功，立刻从"待执行"变为"执行中"并绑定到该设备，其他设备不再能看到它。
- **附带联动动作**：匹配成功时还会顺带完成一些配套事项，例如校验任务所需变量、记录该设备最近执行的任务（供断点续跑类策略使用）、如有应用加固需求则向加固服务登记。

## 匹配结果

- **匹配成功**：任务内容（任务标识 + 要执行的脚本清单 + 目标设备）经长连接下发到上位机，上位机确认领取后开始执行，进入后续的上报流程。
- **没有可匹配的任务**：设备本次落空，等待下一次心跳再试。这是常态，不构成异常。

## 用户可见的表现

- 任务提交后如果长期停留在"待执行"，通常意味着**当前没有满足条件的空闲设备**：检查任务声明的设备/型号/系统要求是否过严，或符合条件的设备是否都在忙、离线或未授权。
- 反过来，设备在线且空闲却一直领不到任务，先确认该设备是否满足任务声明的匹配条件，以及心跳是否正常（见 [上位机长连接](上位机长连接.md)）。
