## 全局关键结论

1. **两条任务调度体系并存**，平台基础功能服务 测试计划按计划类型分流：
   - 新链路：用例（CASE）类计划、任务管理服务 任务模板 → 任务管理服务 自主管道（Redis 队列 + 20s 主动扫描锁设备）→ 设备控制中心，**不经 任务调度服务**。
   - 旧链路：APP 脚本类计划 → app处理服务、Web/桌面类计划 → web/pc处理服务，再经 `action=scheduling, op=Task.init/match` → 任务调度服务（设备心跳触发匹配）。
2. **文件管理服务 与 脚本服务 共享同一套脚本/文件表**（`script_file`、`common_file` 等）：文件管理服务 管上传解析与校验引擎，脚本服务 管 V3 管理台。
3. **文件类资源全链路只传 URL**（appUrl / scriptUrl），上位机/Agent 自行下载，不走文件流。
4. **结果回传路径统一**：上位机 TCP → 设备控制中心 → HTTP → 任务管理服务（或 任务调度服务）→ HTTP 回调 → 平台基础功能服务 汇总通知。
5. **重测 ≠ 补测**：重测是 平台基础功能服务 编排层新建 `RESET_TASK_PLAN` 节点的完整重跑（三出口分流）；补测是执行侧（app处理服务/web/pc处理服务）对漏跑脚本的补充执行，`recoverScriptInfos` 合并进原任务并打补测标记，走 任务调度服务 旧链路。
