# 核心链路-任务执行

> 本服务只承接**用例（CASE）类**任务的新链路，设备分配直推**设备控制中心（real-controlcenter）**，**不经任务调度服务（real-scheduling）**，也不经 app/web 处理服务。
> 触发执行的三条路径：`TaskStartExecuteThread`（20s 扫描，保底） + `TaskExecuteThread`（exec 队列触发全量扫描） + `TaskExecuteStartThread`（execute 分片队列直投单条 executing_report）。

## 概述

提测入队后，执行记录经过「初始化（生成报告行）→ 扫描/队列触发下发 → 锁设备 → 直推设备控制中心 → 设备执行回调」完成自动化测试。全程异步，由 Redis 队列 + 后台线程驱动。

## 阶段详解

### 阶段1: 初始化（TaskInitThread → TaskHandlerServiceImpl.init）

消费队列：`task_execute_record_init_queue`（× `task.init.consumer.count`，默认 20）

1. `TaskInitThread.run` 用 `brPopLPush(init_queue, init_bak_queue)` 可靠取消息，反序列化 `TaskInitRedisDTO{id, count}`；
2. 背压：`taskExecuteRecordJobExecutor` 队列过半先睡 1s；`count > 10` 时把仍为 WAIT_RUNNING 的任务置 EXCEPTION 并补发计划回调；
3. 提交 `taskExecuteRecordJobExecutor.execute` 调 `TaskHandlerServiceImpl.init(id)`（@Transactional）：
   - 抢 `init_task_lock_{id}` 锁，抢不到返回等下一轮；
   - 用例任务走 `initTaskByCase`（用例×数据行生成 `task_execute_record_report_case` + 步骤 DAG）；脚本任务按「脚本×设备」生成报告行 `generateTaskExecuteRecordReport`；
   - 回填 `executeScriptTotal`，条件更新 `WAIT_RUNNING → RUNNING`；
   - 计划任务（`executeRecordTaskId > 0`）插 `task_execute_record_send_task_plan` 并 LPUSH `task_send_plan_queue_{id%20}` 发 INIT_TASK_CALLBACK。

> 注意：init 阶段**不锁设备**，只生成报告行并产出 `task_execute_record_executing_report`（待下发排队凭证）。

### 阶段2: 扫描/触发下发（三条路径汇聚到 TaskHandlerServiceImpl.execute）

- **20s 保底扫描**：`TaskStartExecuteThread.executeTask`，`@Scheduled(cron = "0/20 * * * * ?")`。分两遍扫描 `task_execute_record_executing_report`：先取每个模板最早一条，再处理同模板被跳过的其余记录（防换设备任务饿死）；每条约 `CompletableFuture` 提交 `taskExecuteRecordExecuteExecutor`（固定 50 线程）并发执行；PAUSE 状态跳过。
- **队列快触发（直投单条）**：`TaskExecuteStartThread.run` 常驻 `pop(task_execute_record_execute_queue_{n})`，拿到一条 executing_report 直接调 `taskHandlerService.execute(report, false)`。这是 preComplete 步骤流转后触发下一轮下发的主路径。
- **全量扫描快触发**：`TaskExecuteThread.run` 常驻 `pop(task_execute_record_exec_queue)`，拿到信号即调 `taskStartExecuteThread.executeTask()`（复用 20s 扫描逻辑）。用例任务完成后（`TaskExecuteRecordReportCaseServiceImpl.completeCaseTask`）会 LPUSH 此队列，触发立即扫描。

### 阶段3: 锁设备与下发（TaskHandlerServiceImpl.execute）

1. 任务级 Redisson 锁 `exec_task_report_lock_{taskId}` 防并发计算；`NO_DEVICE(10)` 先 `reOccupyDevice` 重试占用；
2. 已锁设备数 < 需要数时 `occupyOtherDevice` 补占（两轮）；Web/PC 设备按 `ucomId`（上位机）去重，同上位机多设备算一个执行位；
3. 锁/查设备走 `DeviceServiceApi` → **设备控制中心**：`lockTaskExecuteRecordDevice`（V3 `LOCK_DEVICE_BY_TASK_ID`）、`getLockDeviceByTaskExecuteRecordId`；
4. `distributeTaskRecordReportToDevice` 抢 `exec_report_distribute_device{taskId}` 锁，从空闲设备池（`task_execute_record_device_execute_record`）按脚本类型分配设备；
5. 组装 `TaskMatchResponseDTO`（`subTaskId = {taskId}_{deviceRecordId}_{reportId}` + 执行标准 + 全局参数），`DeviceServiceApi.pushTaskDataToDevice` 直推设备控制中心（V1 RPC `op=Task.distributeTask, action=control`）；
6. 下发成功 `afterTaskDistributeSuccess`：报告行 → ING、`matchCount+1`、绑定设备记录。

### 阶段4: 执行监控与回收

设备执行完走两阶段回调（`TaskExecuteRecordController` 的 `/pre_complete`、`/result_report`），详见 [核心链路-结果回收](核心链路-结果回收.md)。

> 「阶段4 超时检查」不存在：`TaskExecuteCheckThread` 整个方法体被注释（死代码），当前无周期性 RUNNING 状态巡检。超时/兜底归因依赖设备侧回调与结果回收管道。

## 涉及表 / Redis key

| 环节 | 表 | Redis key |
|----|------|-----------|
| 初始化 | `task_execute_record_report`(+case/detail)、`task_execute_record_executing_report` | `task_execute_record_init_queue` / bak；锁 `init_task_lock_{id}` |
| 扫描/触发 | `task_execute_record_executing_report` | `task_execute_record_exec_queue`、`task_execute_record_execute_queue_{n}` |
| 锁设备/下发 | `task_execute_record_device_execute_record`、`task_execute_record_report` | 锁 `exec_task_report_lock_{id}`、`exec_task_report_lock_detail_{reportId}`、`exec_report_distribute_device{taskId}` |
| 步骤流转 | `task_execute_record_report`、`..._report_case`、`..._report_detail`、`..._device_execute_record` | `task_execute_record_execute_queue_{n}` / bak |

## 注意事项

1. 20s 扫描是**保底**，不是主路径：正常流转靠 preComplete 里 LPUSH `task_execute_record_execute_queue_{n}` → `TaskExecuteStartThread` 立即直投。
2. 两条队列不要混淆：`task_execute_record_exec_queue`（单条，`TaskExecuteThread` 消费，触发全量扫描）与 `task_execute_record_execute_queue_{n}`（分片，`TaskExecuteStartThread` 消费，直投单条 executing_report）。
3. 任务锁颗粒度是任务级，抢不到直接 `return true` 等下一轮，同一任务下发串行。
