# 用例任务

> 来源：http://test.pro.testin.cn/docs/case/case_task/

将多个测试用例聚合到一个任务中统一执行，包含任务模板、模板触发执行记录、任务报告。

点击`测试管理`/`用例任务`。

## 任务模板
创建任务模板，可多次触发执行。

使用流程如下：

1. 创建任务模板。
2. 设置任务执行策略。
3. 设置执行设备。
4. 触发执行。

### 创建任务模板
填写任务名称及任务描述信息。

规划&执行：创建任务模板并进入模板配置，选择测试用例、设置执行策略、选择测试设备。

也可点击`任务模板名称`进入模板配置。

#### 关联测试计划模板
用例任务模板可查看已关联测试计划模板，已关联测试计划的任务模板不可删除，删除前可点击`已关联测试计划模板`查看关联关系，在`测试计划模板`/`已关联任务`中解除关联关系后，可操作删除。

#### 模板类型与状态

（本节规则细节来自 04 专题，见 [04-横切-任务状态机](../04-复杂功能细节/横切-任务状态机.md) 与 [04-核心链路-定时任务模板执行](../04-复杂功能细节/核心链路-定时任务模板执行.md)。）

模板分两种类型：**普通模板**（只能手动点执行）和**定时模板**（挂 cron 表达式，到点自动生成执行记录）。定时模板让"每天凌晨跑一轮回归"这类场景无需人工触发。

模板自身有两个管理状态：

| 状态 | 含义 |
|---|---|
| 运行中 | 模板处于活跃状态；定时模板正常参与调度 |
| 已暂停 | 定时调度自动跳过该模板，不产生新执行；可恢复，恢复后继续按 cron 触发 |

模板支持批量暂停 / 批量恢复 / 删除；已删除的模板不再参与任何调度。

定时模板的触发与补偿规则：

- 平台按模板的 cron 表达式周期扫描，到点即为该模板创建一条执行记录，来源标记为"定时任务"。
- 定时触发生成的执行记录与手动提测完全一致：从模板加载脚本 / 用例 / 设备 / 执行配置做快照，然后进入标准的设备匹配 → 下发 → 监控 → 回收管道；之后修改模板不影响已生成的执行记录。
- 如果某次定时触发因异常未能成功生成执行记录，平台有独立的补偿检查：定期扫描是否有漏掉的定时执行，发现后自动补触发，保证"到点必跑"。

### 测试用例
查看已添加测试用例。

点击`添加用例`为任务模板添加用例。

- 添加用例时，已添加用例会在用例列表中处于已勾选状态，可快速区分当前已添加的用例。

- 若用例数量很多，想要一键全部添加，可手动修改每页显示条数，最多可支持`1000条/页`，通过当前页全选实现快速选择。

### 执行策略
设置用例任务模板的执行策略。

#### 待测应用类型
系统按照任务模板选择的测试用例，根据用例关联的脚本类型，自动匹配并显示待测应用类型，不可人工修改。

#### App应用提测方式
待测应用类型中包含App时，需要设置该项。

**无应用提测**

任务初始化时，手机设备无需安装应用，可在脚本步骤中通过“安装应用”与“启动应用”来准备待测应用。

**安装待测应用**

需要选择待测应用安装包。

点击`下一步`选择应用安装包。

**使用最新上传的安装包**

开启后，使用`应用管理`/`应用文件夹`内，相同包名最新上传的应用安装包。

#### 执行方式
分布式执行：测试用例随机下发至设备并行执行。

设备驱动执行：按顺序将测试用例下发到所有关联设备，设备仅执行与自身类型匹配的用例步骤，无法匹配的步骤自动跳过。用于测试计划中在核心测试任务前后，对设备进行初始化或数据清理。（设备驱动执行方式时，不支持设置数据源及数据标签）

#### 数据源
任务执行时选择数据源后，通过测试用例关联数据源中的用例数据表，可以使同一个用例在任务执行时基于不同的数据行重复运行，从而覆盖更多测试场景，提高测试效率与覆盖率。测试用例关联用例数据表

#### 数据标签包含
选择数据源后，通过数据标签来筛选需要执行的数据行，未设置数据标签时，默认执行数据源用例表中的所有数据；设置多个标签时，按'或'关系匹配，数据行包含任一标签则执行。

#### 执行环境
支持自定义环境执行。 环境管理

- 用例中关联Web脚本时，`访问URL`时，默认通过本地Host访问，不单独指定Host，可通过执行环境配置Host访问客户产品所在的环境。
- 用例中关联App脚本时， 在脚本步骤中使用`数据库操作`步骤，可通过环境切换脚本中步骤连接的数据库。

#### 步骤全局超时时间
任务执行时默认使用脚本步骤中设置的超时时间，若该任务执行时有性能要求，可设置任务步骤全局超时时间，修改后脚本步骤中使用全局超时的步骤都将按照任务设置的步骤超时时间执行。

#### 录制视频
用例关联脚本执行时录制视频，用于执行失败时辅助分析并定位执行未通过的原因。

#### 设备不可用时
等待设备恢复并继续执行：任务执行中，若设备离线则等待设备再次上线后继续执行，用于设备不稳定时，临时离线后很快再次上线的场景。

将测试用例执行状态标记为已跳过：任务执行中，若设备离线则将执行中的用例标记为已跳过，避免长时间等待设备恢复，导致无法继续执行任务。

### 测试设备
系统根据选择测试用例自动判断测试需使用的设备，如：用例关联脚本类型包含App、Web、桌面时，则需要选择对应执行端类型的测试设备。

#### 安卓设备网络
任务执行时，可设置安卓手机设备的网络环境，默认为Wi-Fi环境，可进行切换。

**Wi-Fi：**默认Wi-Fi下执行任务，若手动关闭了设备Wi-Fi，系统检测到任务需要在Wi-Fi网络下执行，上位机会自动开启设备Wi-Fi。

**SIM卡网络：**已选设备安装了SIM卡且开启了网络，优先使用SIM卡网络执行脚本，若已选设备未插入SIM卡则脚本执行失败。

**模拟网络：**通过Wi-Fi网络可模拟2G、3G、4G、5G不同网络下的执行情况，模拟网络需要在管理中心配置 。如何配置？

## 提测与执行过程

（本节规则细节来自 04 专题，见 [04-核心链路-任务提测](../04-复杂功能细节/核心链路-任务提测.md) 与 [04-核心链路-任务执行](../04-复杂功能细节/核心链路-任务执行.md)。）

### 提测规则

一次提测可以携带：脚本清单或用例清单、目标设备、执行配置（超时、加速、采集开关等）、通知配置、允许执行的时间段。提交成功即返回执行记录 ID，后续进度、报告都围绕这条记录展开。

- **两种组装方式**：按模板提测（指定模板，从模板加载脚本 / 用例 / 设备等配置），或无模板直接提测（临时选定脚本与设备直接提交）。
- **配置快照**：提测时会把当时的全部配置（脚本 / 用例 / 设备 / 执行标准 / 通知 / 时间段）整体快照到执行记录上，**之后修改模板不会影响已创建的执行记录**。
- **初始状态**：App 任务用安装包 URL 提测（尚未有安装包 ID）时，先进入"等待 App 处理"状态，等安装包下载安装完成后再进入待执行；其余任务直接进入"待执行"。

每条执行记录都会标记来源，影响完成后的结果回传方式：

| 来源 | 触发方式 |
|---|---|
| 手动 | 用户直接提测（重测也视为手动，见下文批量重测） |
| 定时任务 | 定时模板到点触发 |
| 测试计划 | 被测试计划编排触发，完成后结果回传计划侧 |
| 重测 | 基于已有执行记录重建 |

### 执行的四个阶段

提测后执行记录依次经过四个阶段完成自动化测试，全程异步，无需人工值守：

1. **初始化（设备匹配）**：平台按任务要求的设备向设备控制中心申请锁定设备；匹配成功则记录设备分配结果，匹配失败则任务标记为失败并通知相关方。
2. **启动执行**：把脚本 / 用例、设备分配结果和执行参数一并下发到执行侧，任务状态变为"执行中"。
3. **执行监控**：执行期间平台持续轮询任务进度，实时更新已执行数、成功数、失败数等统计；任务完成后进入结果回收管道。
4. **超时检查**：平台定时扫描执行中的任务，超过最大执行时间的标记为"超时"并通知相关方；配置了执行时间段限制的任务，只在允许的时间段内执行（超出时段按配置暂停推进）。

## 执行记录
任务模板触发执行后，产生执行记录。

| 序号 | 字段 | 说明 |
|---|---|---|
| 1 | 预期执行用例数 | 预期执行用例数=任务提测用例数x用例数据表数据，预期要执行的用例总数。 |
| 2 | 设备数 | 设备数，设备异常时可查看可用设备/设备总数 |
| 3 | 执行用例通过率 | 执行用例通过率=（通过数/预期执行用例数）x 100% |
| 4 | 有效执行时长 | 统计至少一个用例在执行的时间段，以评估有效执行的总耗时。 |
| 5 | 执行状态 | 未开始：任务创建后队列未处理到该任务。 执行中：任务进入初始化阶段。 已取消：用户手动终止任务执行。 已完成：任务中所有用例执行完毕，产生测试结果。 |
| 6 | 用例执行进度 | 预期执行用例数、实际执行用例数、执行状态分布：待执行、执行中、已执行（通过）、已执行（未通过）、已跳过、已取消。 |

注：若任务存在多次重测后，任务汇总记录，在计算预期执行用例数、设备数、执行进度时数据时将排重处理，有效执行时长则汇总统计。

### 执行状态的完整含义与统计口径

（本节规则细节来自 04 专题，见 [04-横切-任务状态机](../04-复杂功能细节/横切-任务状态机.md)。）

上表"执行状态"是列表页的展示口径；平台内部每条执行记录在以下状态间流转：

| 状态 | 含义 |
|---|---|
| 待执行 | 已创建，等待进入执行管道（正常流程的初始状态） |
| 等待 App 处理 | App 任务用安装包 URL 提测，安装包下载安装中；完成后由脚本服务通知，自动转为待执行 |
| 执行中 | 设备匹配并下发成功，正在设备上执行 |
| 成功 | 全部脚本 / 用例执行通过（结果回收完成后按通过情况落入成功或失败） |
| 失败 | 存在失败或全部失败的脚本 / 用例 |
| 已取消 | 用户主动取消（待执行、等待 App 处理、执行中均可取消） |
| 超时 | 超过最大执行时间或超出允许执行时间段，由超时检查落入 |

每条执行记录跟踪六类统计，脚本和用例两个维度分别计数：

| 统计 | 含义 |
|---|---|
| 已执行数 | 实际分配到设备执行的 |
| 成功数 | 执行通过 |
| 失败数 | 执行失败 |
| 跳过数 | 条件不满足被跳过 |
| 取消数 | 用户取消 |
| 超时数 | 超过最大执行时间 |

点击`执行记录名称`跳转至执行用例记录，可查看每个用例执行记录，可人工自定义测试结果、问题类型、错误原因，如：脚本或用例执行后由于业务检查点步骤检查文案显示不正确导致脚本执行失败，文案显示问题属于建议优化类问题，不影响核心功能流程，可人工设置脚本或用例执行测试结果为通过，无需重复测试，修改测试结果后报告统计数据将同步更新。鼠标悬停测试结果、问题类型、错误原因可操作修改。

当用例执行未通过后，若匹配到人工提前预置的规则，则自动将未通过的问题类型及错误原因标记为匹配到的结果。如何预置问题类型及错误原因？

预置规则的效果：对网络、环境等非应用原因导致的失败设置相应规则后，系统在自动化执行过程中会根据规则自动判断并标记为误报类型。

点击操作列`查看详情`，可查看用例关联脚本的详细执行记录。

点击`调试用例`可跳转至录制工具中调试用例。

### 编辑问题属性
分析执行记录确定失败原因，相同错误原因可人工操作批量标记错误类型及原因。

选择`用例执行记录`/`点击编辑问题属性`，批量设置测试结果、问题类型及原因。

### 批量重测
执行用例未通过时，可修改测试用例后批量重测，将选择的执行用例及执行数据，重新聚合到一个任务中重新执行。

重测的底层规则（细节来自 04 专题，见 [04-核心链路-任务重测](../04-复杂功能细节/核心链路-任务重测.md)）：

- 重测时只需指定父任务（一条已有执行记录），平台自动复制父任务的全部执行配置，无需重新组装；允许在重测时修改任务名称（不改则沿用父任务名）。
- 重测任务的来源标记为"手动"——重测被视为一次人工操作。
- 可以携带额外的重置配置：例如指定只重测部分脚本 / 用例、更换设备、覆盖环境变量。
- **重测不走模板**：即使父任务来自模板，重测也直接复制父任务快照，不重新读模板（因此模板后续修改不影响重测）。
- 每次重测都会记录父任务，形成"原始任务 → 第一次重测 → 第二次重测"的可追溯父子链；多次重测之间互相独立，每条重测任务有自己的状态、进度和报告。
- 重测任务与父任务互不影响：状态独立、通知可配置为与父任务不同、产出自己的执行报告；重测任务与手动提测走完全相同的执行管道。

### 重测修改设备
为确保测试结果的一致性和可对比性，重测用例默认优先使用原执行设备。开启重测修改设备后，将以新勾选的设备为准触发重测执行。

注意：

- 重测报告数据将与首轮报告数据汇总到同一报告中展示。

- 重测时默认使用任务模板触发那一刻的任务快照触发执行，可设置重测策略。

- 重测时若测试用例及执行数据发生变更后，将使用最新的数据执行。

## 任务报告
任务执行完后后，可点击任务执行记录操作列查看报告。

执行用例记录。

注：若从汇总任务点击查看报告时，执行用例记录为聚合多轮任务执行后的数据，同一用例及数据行多次执行仅显示最后一次执行记录。

### 结果回收管道

（本节规则细节来自 04 专题，见 [04-核心链路-结果回收](../04-复杂功能细节/核心链路-结果回收.md)。）

任务执行完成后，执行侧把原始执行数据回传，平台经过三个阶段把它转化为结构化报告并通知调用方：

1. **结果解析**：把执行侧返回的原始数据拆解为结构化结果，按脚本维度（执行状态、日志、错误信息、截图）、用例维度（每个用例的执行结果）、步骤维度（用例内每个步骤的执行明细）分别落库；解析历史留痕，便于追溯。
2. **统计分析**：聚合单个任务的全部结果，按结果分类（成功 / 失败 / 跳过 / 取消 / 超时，脚本与用例两个维度分别统计）和错误类型分布更新任务统计数字，支撑报告页的错误归因视图；分析历史同样留痕。
3. **结果回传**：按任务来源决定结果去向——测试计划来源的结果回传给平台基础功能服务的计划侧，驱动计划进度；手动 / 定时 / 其他来源通过通知渠道（邮件 / IM 等）告知相关人。每次回传都会记录回传状态，可查询是否成功送达。

三个阶段任何一步处理失败都不会丢数据：失败的消息进入补偿队列，由独立的补偿机制自动重试直到成功，用户无需干预。
