# 结果回收与报告汇总实现

## 概述

设备侧执行完成后，结果经「解析 → 分析 → 统计聚合」落库，并把执行进度/结果回调给平台基础功能服务。本文对齐代码讲清三段的核心方法：`TaskResultHandlerServiceImpl.taskResultParse`（解析）、`taskResultAnalysis`（分析）、`TaskExecuteRecordReportServiceImpl.dealReportResultByReport`（统计聚合）与 `TaskExecuteRecordReportCaseServiceImpl.completeCaseTask`（用例汇总）。

> 队列/线程拓扑见 [核心链路-结果回收](../04-复杂功能细节/核心链路-结果回收.md)，本文只讲落库与计算逻辑。

## 阶段1：结果解析（taskResultParse）

`TaskResultHandlerServiceImpl.taskResultParse`（`@Transactional`），由 `TaskResultParseThread` 消费 `task_result_parse_queue_{n}` 触发：

1. 抢 Redisson 锁 `task_result_parse_{resultUrl}`（常量 `TASK_RESULT_PARSE`），抢不到直接返回。
2. 调脚本服务 `getTaskUrlParseResult` 查结果文件解析状态，三分支：
   - `PARSE_ERROR`（或 `parseCount > 50` 且超时）→ `dealReportResultWithErrorByNoSwjReport` 按 `PARSE_ERROR` 归因落库；
   - `PARSING` → `parseCount + 1` 重投 `task_result_parse_queue_{n}` 继续等；
   - `PARSED` → 插 `task_execute_record_result_analysis` 待办，删解析待办，LPUSH `task_result_analysis_queue_{n}`。

## 阶段2：结果分析（taskResultAnalysis）

`TaskResultHandlerServiceImpl.taskResultAnalysis`，由 `TaskReportResultAnalysisThread` 消费 `task_result_analysis_queue_{n}` 触发：

1. **并发控制**：抢锁 `result_analysis_{resultUrl}`（常量 `RESULT_ANALYSIS_LOCK`），防止同一条结果被多线程重复分析。
2. **兜底**：`analysisCount > 50`（`MAX_TIME / 2`）时抢 `result_analysis_{taskId}` 锁，按 `PARSE_ERROR` 兜底归因后删待办返回。
3. **取结果文件**：`scriptService.getTaskUrlParseResult` 拿 summary / logRes / testCase 等结果文件 URL，`fileUtil.saveToFile` 落本地。
4. **解析三文件**：
   - `TaskReportSummaryInfoDTO.parseSummaryXmlFile`（summary XML，含 `reportRunInfo`）；
   - `TaskReportLogSummaryDTO`（logRes JSON）；
   - `TaskReportTestCaseDTO.parseTestCaseXml`（testCase XML，含步骤 OCR）。
5. **错误码映射**：`systemServiceApi.getErrorCode(errorCode, fromWarningCode)` → `ErrorCodeDTO.getResultCategory()` 得 `resultCategory`；`SUCCESS` 时清空 `errorMsg`。
6. **重新上传**：解析后的 summary / logSummary / testCase 经 `FileUploadServiceApi.uploadFile` 生成新 URL，写回 `task_execute_record_report_detail.resultDetail`（`TaskReportDetailResultDTO` 数组，含 `summaryUrl/logSummaryUrl/testCaseUrl/subTestCaseUrl/videoUrl` 等）。
7. **耗时回填**：遍历 `reportRunInfo.testProcesses` 各阶段（`TaskProcessStageTypeEnum` INIT/PREPARATION/EXECUTE/CLEANUP）累加 `scriptInitCostTime / scriptPreparationCostTime / scriptStepCostTime / executeCostTime`，并按首尾时间回填 `executeStartTime / executeEndTime`。
8. **错误原因规则匹配**：`systemServiceApi.getErrorCauseMathRule` 拉规则，命中 `errorMsg`（或 OCR 文本）时回填 `errorCodeId` / `errorCauseLogName` / `executeResultSummary`（详见下文）。
9. **结果分类**：`resultCategory == SUCCESS` → 报告行 `SUCCESS(2)`，否则 `FAIL(3)`。
10. **聚合**：抢 `result_analysis_{taskId}` 锁，`dealReportResultByReport` 聚合任务统计，最后删分析待办。

## 阶段3：统计聚合（dealReportResultByReport）

`TaskExecuteRecordReportServiceImpl.dealReportResultByReport`：

- 通过 `TaskExecuteRecordMapper.addCostTimeAndScriptInfoByCondition` **原子累加** `task_execute_record` 上的脚本/用例两维度各 6 个计数（`execute/success/fail/skip/cancel/timeout × script/case`），并回填 `executeCostTime`。
- 有效执行时长：脚本侧 `calculateExecuteValidTime`，用例侧 `calculateExecuteValidTimebyCase`。
- 全部报告行终态时聚合任务状态（`RUNNING → FINISH`）。

> 计数口径与 6 个字段含义见 [横切-任务状态机](../04-复杂功能细节/横切-任务状态机.md) 的「用例/脚本结果统计口径」。

## 用例报告汇总（completeCaseTask）

`TaskExecuteRecordReportCaseServiceImpl.completeCaseTask`（两个重载）：

- 用例 × 数据行维度的结果聚合：累加 `task_execute_record` 上的用例计数（`*CaseTotal`）；
- 用例任务完成时触发 `TaskExecuteThread`（LPUSH `task_execute_record_exec_queue` 单条信号）立即扫描，而不是等 20s 保底。

## 兜底归因（dealReportResultWithErrorByNoSwjReport）

`TaskExecuteRecordReportServiceImpl.dealReportResultWithErrorByNoSwjReport`（两个重载）：

- 结果文件缺失 → `NO_RESULT_INFO`；解析失败/超时 → `PARSE_ERROR`；设备环境异常（`resultType=EXCEPTION`）→ `ENV_FAILED`。
- 走「无结果文件」路径直接落库归因，不阻塞任务流转。

## 涉及表 / Redis key

| 环节 | 表 | Redis 锁 |
|------|-----|---------|
| 解析 | `task_execute_record_result_parse` | `task_result_parse_{resultUrl}` |
| 分析 | `task_execute_record_result_analysis`、`task_execute_record_report` / `_detail` | `result_analysis_{resultUrl}` / `result_analysis_{taskId}` |
| 统计聚合 | `task_execute_record`（计数 + 耗时）、`task_execute_record_report` | `result_analysis_{taskId}` |
| 用例汇总 | `task_execute_record_report_case` | — |

## 注意事项与坑

1. **重试上限不对称**：解析/分析等待用的是「次数累加」（`parseCount` / `analysisCount`），分析兜底阈值 50（`MAX_TIME/2`）与回调丢弃阈值 100（`MAX_TIME`）是两套常量，别混。
2. **两个 result_analysis 锁语义不同**：`result_analysis_{resultUrl}` 防同一结果文件重复分析；`result_analysis_{taskId}` 防同一任务的统计聚合并发——后者在 `dealReportResultByReport` 前才抢。
3. **错误原因匹配是「先 errorMsg 后 OCR」**：命中任一即 break，`errorMsg` 优先；`executeResultSummary` 在有 `errorCodeId` 时覆盖为 `errorCodeId`。
4. **结果文件重上传**：分析会把解析后的 summary/log/testCase 重新上传文件服务生成新 URL，旧 URL 只是解析来源，最终对外暴露的是新 URL。
5. **`dealReportResultByReport` 的原子累加依赖 SQL 条件**：计数更新必须走 `addCostTimeAndScriptInfoByCondition` 的条件累加，避免并发分析导致计数翻倍。
