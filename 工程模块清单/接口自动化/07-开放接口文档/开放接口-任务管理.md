# 开放接口-任务管理

> 三个端点：`task/create`（以脚本提测，触发执行）、`scriptRunInfos`（查执行结果）、`saveTaskCase`（维护任务与用例的关联）。如果要跑的是**任务**而不是单脚本，用 [开放接口-通用调用](开放接口-通用调用.md) 的 `Task.run`。

## POST /open/task/create

以脚本提测：把指定脚本在指定环境上**立即执行一次**（异步）。典型场景：CI 构建后触发冒烟脚本。

**请求参数：**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| thirdProjectId | string | **是** | 项目 ID |
| scriptId | string | **是** | 脚本 ID（来自 [开放接口-脚本查询](开放接口-脚本查询.md)） |
| envId | string | **是** | 环境 ID（来自 [开放接口-环境查询](开放接口-环境查询.md)） |
| paramList | array | 否 | 变量覆盖：`[{"k": "变量名", "v": "变量值"}]`，执行时注入 |

```bash
curl -X POST 'http://<host>/open/task/create' \
  -H 'Content-Type: application/json' -H 'Sid: <sid>' \
  -d '{"thirdProjectId":"1","scriptId":"cea7a127-...","envId":"2c4eb367-...","paramList":[{"k":"userId","v":"1001"}]}'
```

**响应（`R` 包装）**：`data` 为**报告 ID 字符串**（UUID）。

```json
{"code": 0, "msg": "成功", "data": "8cf598b7-0f87-4171-a38a-13594364dce8"}
```

**注意事项：**

1. ⚠️ **scriptId 不存在时返回 `code:0` 但 `data` 为 null**——静默成功，务必判空。
2. ⚠️ 返回的"报告 ID"**不是任务报告**，是脚本执行结果记录的 ID，只能拿它调下面的 `scriptRunInfos`；拿去查任务报告接口（`Report.get`）会查不到。
3. 执行是异步的：拿到报告 ID 后需要轮询 `scriptRunInfos` 直到状态到终态。
4. 每次调用都真实执行一次，无幂等去重——重复调用会产生多条执行记录。

## POST /open/task/scriptRunInfos

查询 `task/create` 触发的脚本执行结果。

**请求参数：**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| reportId | string | **是** | `task/create` 返回的报告 ID |

**响应**：`data` 为执行结果对象：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | string | 结果 ID（即报告 ID） |
| name | string | 名称（脚本名或报告 ID） |
| resourceId | string | 绑定的脚本 ID |
| status | string | 运行状态（运行中 / 结束等） |
| exeResult | string | 执行结果：成功 / 失败（**终态判断用 status + exeResult 组合**） |
| content | string | 执行详情（JSON 字符串：请求/响应/断言明细） |
| startTime / endTime | long | 起止毫秒时间戳 |
| reportType / type | string | 类型标记（script / SCRIPT） |
| envConfig | string | 执行时的环境配置快照（JSON 字符串） |

```json
{"code": 0, "msg": "成功", "data": {
  "id": "8cf598b7-...", "name": "登录冒烟", "resourceId": "cea7a127-...",
  "status": "结束", "exeResult": "成功",
  "startTime": 1690000000000, "endTime": 1690000002300, "type": "SCRIPT"
}}
```

**注意事项：** reportId 不存在时 `data` 为 null（不报错）；轮询建议间隔 2-3 秒，超时上限自定（执行机上 JMeter 跑脚本通常秒级，复杂编排可能分钟级）。

## POST /open/task/saveTaskCase

保存**任务与用例的关联关系**（决定一个任务里有哪些用例、顺序如何）。

**请求参数：**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| id | string | 否 | 任务 ID；**不传时按 `name + projectId + taskModuleId` 反查任务** |
| projectId | string | 是 | 项目 ID |
| name | string | 反查时必填 | 任务名称（仅 id 为空时用于反查） |
| taskModuleId | string | 反查时必填 | 任务目录 ID（仅反查用） |
| caseInfo | string | 是 | **JSON 字符串**：用例数组，如 `"[{\"id\":\"caseId1\"},{\"id\":\"caseId2\"}]"`，数组顺序即执行顺序 |
| tag / executor | string | 否 | 任务标签 / 负责人（保存语义不涉及，可忽略） |
| retestNum | int | 否 | 失败重测次数 |
| sid | string | 否 | 也可放 body 里鉴权 |

**响应**：`R` 包装，`data` 为空。

**注意事项（高风险，务必读）：**

1. ⚠️ **覆盖语义：先清空该任务的全部用例关联，再按 caseInfo 全量插入**。想"增量加一条用例"必须先把现有关联全量带上，否则界面上的既有配置会被清掉。
2. ⚠️ id 为空且按名称反查不到任务时**静默返回成功**（log 记"未找到匹配的任务"），调用方无法从响应区分"保存成功"与"什么都没做"。建议总是显式传 `id`。
3. 用例顺序号（caseNum）按 caseInfo 数组下标从 1 生成——**caseNum 是执行结果对位锚点**（见 [批次结果聚合](../03-实现逻辑/批次结果聚合.md)），重复调用且顺序不同会让同一任务的前后两次报告不可比。
4. caseInfo 里每个元素只要 `id` 字段（用例 ID），多余字段被忽略；传不存在的用例 ID 不做校验。
