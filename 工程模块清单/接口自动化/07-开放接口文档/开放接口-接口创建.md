# 开放接口-接口创建

> 向平台登记一个接口定义（资产入库）。接口的业务含义见 [接口管理](../01-产品功能/接口管理.md)。

## POST /open/interface/add

创建接口。典型场景：CI 同步契约仓库中的接口定义到平台。

**请求参数（顶层）：**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| projectId | string | **是** | 项目 ID（注意：不是 thirdProjectId） |
| name | string | **是** | 接口名称，**同模块下唯一**，重复报"接口名称已存在" |
| protocol | string | **是** | 协议：HTTP / DUBBO / T2 / SQL 等 |
| method | string | **是** | 请求方式（GET/POST…；非 HTTP 协议按平台约定填） |
| moduleId | string | **是** | 模块 ID（来自 [开放接口-项目与模块查询](开放接口-项目与模块查询.md)） |
| status | string | **是** | 状态：设计中 / 已启用 / 已废弃 |
| serverId | string | **是** | 服务 ID（按服务分组） |
| requestParam | object | **是** | 请求参数结构（见下） |
| response | object | **是** | 返回参数结构（见下） |
| id | string | 否 | 传了则名称查重时排除该 id（平台按新建处理，不会更新已有记录） |
| path | string | 否 | 请求路径 |
| description | string | 否 | 描述 |
| tags | string | 否 | 标签 |
| sid | string | 否 | 创建人识别（也可走 `Sid` 头） |

**requestParam 结构**（对应平台的请求参数模型）：

| 字段 | 必填 | 说明 |
|---|---|---|
| headerList | 否 | 请求头 `[{name, value, ...}]` |
| queryList | 否 | query 参数列表 |
| restfulList | 否 | restful 路径参数列表 |
| beforeActionList | **是** | 前置动作列表（可为空数组） |
| afterActionList | **是** | 后置动作列表（可为空数组） |
| assertionRuleList | 否 | 断言规则列表 |
| body | **是** | 请求体对象（至少传空结构） |
| tcpRequestParameters | **是** | TCP 参数（非 TCP 协议也**必须传**，可空对象） |
| dubboRequestParameters | **是** | Dubbo 参数（同上） |
| webSocketRequestParameters | **是** | WebSocket 参数（同上） |
| grpcRequestParameters | **是** | gRPC 参数（同上） |
| graphQLRequestParameters | 否 | GraphQL 参数 |

**response 结构**：`{"body": {...}}`，body 必填（可空结构）。

> ⚠️ **必填校验的坑**：requestParam 里 before/after/body 和四个协议参数块都标了非空校验——即使创建的是纯 HTTP 接口，也要把 `tcpRequestParameters`、`dubboRequestParameters`、`webSocketRequestParameters`、`grpcRequestParameters` 以空对象 `{}` 传上，否则报参数校验错误（`10005`）。这与前端保存接口时给七个协议块兜底的逻辑一致（见 [接口管理实现](../03-实现逻辑/接口管理实现.md)）。

**请求示例：**

```bash
curl -X POST 'http://<host>/open/interface/add' \
  -H 'Content-Type: application/json' -H 'Sid: <sid>' \
  -d '{
    "projectId": "1", "name": "查询订单", "protocol": "HTTP", "method": "GET",
    "path": "/order/query", "moduleId": "mod-123", "status": "已启用", "serverId": "srv-1",
    "requestParam": {
      "headerList": [], "queryList": [], "restfulList": [],
      "beforeActionList": [], "afterActionList": [],
      "body": {}, "tcpRequestParameters": {}, "dubboRequestParameters": {},
      "webSocketRequestParameters": {}, "grpcRequestParameters": {}
    },
    "response": {"body": {}}
  }'
```

**响应（`R` 包装）**：`data` 为创建成功的接口完整对象（含分配的 `id`、`interfaceNumber` 编号、格式化后的 `requestParam`/`response` JSON 字符串、`createTime` 等）。

**行为说明：**

1. 接口编号（interfaceNumber）由平台按项目内自增分配。
2. body 为 JSON 时会自动生成/更新 jsonSchema 描述。
3. 如果 requestParam 的 `body.bodyFormData[0].fileIds` 含文件 ID，平台会把这些文件关联到新接口（文件需先存在）。
4. requestParam/response 在入库前会经过一次字符串格式化，返回内容里这两字段是**格式化后的 JSON 字符串**（不是对象），含特殊字符的值建议创建后回读校验。
