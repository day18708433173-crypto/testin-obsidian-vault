# 后端双形态架构

## 一份代码、两种运行形态

`testin-api-backend` 仓库里只有一份 Java 源码，但通过两个 pom 打出**两个可独立部署的服务**：

| 形态 | 入口类 | 构建命令 | artifactId | 进程模型 |
|---|---|---|---|---|
| 服务端（管理 + 调度） | `cn.testin.Application` | `mvn package`（`pom.xml`） | `testin-api-backend` | Spring Boot 2.3.1 + Jetty |
| 执行端 / 执行机（runner） | `cn.testin.runner.RunnerApplication` | `mvn package -f runnerPom.xml` | `testin-api-backend-runner` | **非 Spring**，`main` 手动初始化 |

### 服务端

- Spring Boot 2.3.1，内嵌 **Jetty**（pom 里显式排除了 Tomcat，见 `pom.xml` 中 spring-boot-starter-web 的 exclusion 与 spring-boot-starter-jetty 依赖），端口 `8526`。
- 提供全部 REST 接口：用例/脚本/环境/报告/测试机管理等。
- **内嵌 xxl-job 2.4.0 管理台**：`controller/xxljob/` 是 xxl-job admin 的页面接口，`xxl.job.admin.addresses` 指向自身 `http://127.0.0.1:8526/job`；执行器注册名 `testin-task-job-executor`，端口 8889。详见 [定时调度体系](../03-实现逻辑/定时调度体系.md)。
- 入口 `Application.main` 第一行设置 fastjson 安全模式 `ParserConfig.getGlobalInstance().setSafeMode(true)`，并启动 `TestMachineService.initRunner()` 监听执行机在线状态（见 [测试机管理](../01-产品功能/测试机管理.md)）。

### 执行端（runner）

- **不是 Spring 应用**：`RunnerApplication.main` 里手动 new 出各组件，按位置参数启动：

  ```
  <HTTP_PORT> <REDIS_HOST> <REDIS_PORT> <REDIS_DB> <REDIS_PASSWORD|"EMPTY_PASSWORD"> [JMETER_HOME]
  ```

- 启动顺序：先起一个 Jetty HTTP 端口（`RunnerServletController`）等服务端调用来初始化 machineId → 然后 `RunnerConsumer.runnerJedisLinter` 在自己专属的 Redis list 上 `brpop` 死循环等任务。
- 内嵌 JMeter 5.5 引擎（`JmeterServiceConfig` 初始化），任务本体是 JMX，从 Redis 取回后本地执行。
- 完整启动细节见 [执行端Runner详解](../03-实现逻辑/执行端Runner详解.md)。

## 两端如何通信

**没有 RPC、没有 HTTP 回调主链路**——两端只靠 Redis key + 序列化 DTO 通信：

```
服务端                                    Redis                         执行端
──────                                    ─────                         ──────
TestExecuteService
TestAutomationService
   │ 生成 JMX
   ▼
ServerProducer ── set JMX ──────────► getJmeterRunIdRedisKey(runId)
   │ lpush 任务引用
   ▼
              ──► getRunnerLinterRedisKey(machineId) ──► brpop ──► RunnerConsumer
                                                                       │
                                                          get JMX ◄───┘
                                                                       ▼
                                                          RunnerTestExecuteService
                                                                       │ JmeterServiceConfig 起引擎
                                                                       ▼
                                                          结果回写 Redis / 回传服务端
```

- 所有 Redis key 集中在 `src/main/java/cn/testin/commons/utils/RedisKeyUtil.java`，完整 key 清单见 [Redis通信与Key设计](../03-实现逻辑/Redis通信与Key设计.md)。
- 批次执行结果由服务端 `TestTaskBatchPoller`（`@Scheduled` 每 3s 轮询活跃批次）聚合，见 [批次结果聚合](../03-实现逻辑/批次结果聚合.md)。
- 执行端自己的 redis 客户端在 `runner/jedisConfig/`（RunnerProducer / RunnerConsumer / JedisPoolManager），与服务端 `config/redisConfig/`（spring-data-redis）是**两套独立实现**。

> **跨端修改警告**：改 `JmeterRunRequestDTO` 等传输对象、或 `RedisKeyUtil` 里的 key 结构时，两个 pom 产物（服务端 + runner）必须**同时重新构建部署**，否则线上会出现"任务发了没人执行"或"执行了结果读不到"。

## 代码结构地图（服务端为主）

```
src/main/java/cn/testin/
├── Application.java            # 服务端入口（fastjson safemode、initRunner）
├── CORSFilter.java
├── controller/                 # REST 接口，@RequestMapping("/case") 风格，无统一前缀
│   ├── xxljob/                 # 内嵌 xxl-job admin 页面接口
│   └── OpenApiController.java  # 对外开放接口（另一套鉴权）
├── interceptor/                # KeyInterceptor(真权限) / AuthInterceptor(假实现) / RewriteDispatcherServlet
├── service/
│   ├── execution/              # 执行编排（触发→分发）
│   ├── jmeter/                 # JMX 生成 / 解析
│   ├── nosql/                  # HBase / Phoenix / Mongo 数据源测试
│   ├── plan/                   # 测试计划
│   └── openApi/
├── runner/                     # 执行端专属代码
│   ├── RunnerApplication.java  # 执行端入口
│   └── jedisConfig/            # 执行端自己的 redis 客户端
├── xxljob/                     # xxl-job jobhandler
├── schedule/                   # @Scheduled 简单定时任务
├── protocol/fix/               # QuickFIX/J 的 FIX 协议支持（证券接口）
├── config/Listener/t2/ + extension/t2/  # 恒生 T2 协议
├── mapper/                     # MyBatis mapper 接口 + XML（同目录！）
├── dao/                        # DO；entity/ 放实体与 DTO
└── commons/
    ├── constants/              # 业务枚举/常量总入口 ApiTestConstants
    ├── utils/                  # RedisKeyUtil、LogUtil 等
    ├── Response/  exception/
```

**MyBatis XML 的特殊位置**：XML 与 mapper 接口同目录放在 `src/main/java/cn/testin/mapper/` 下，靠 pom 的 build resources 配置把 `src/main/java/**/*.xml` 拷进 classpath——不要按 Spring 惯例去 `resources/` 下找 mapper xml。

## 类加载顺序约定（重要坑）

`lib/` 下的三个 jar 以 **system scope** 引入：

- `ApacheJMeter-associate-api-functions.jar`
- `testin-protobuf-java-3.17.1.jar`
- `protobuf-java-util-3.17.1.jar`

原因（pom 注释原文）：第三方开源 jar 与 JMeter 自带的包冲突，artifactId 命名尽量靠前，**部署时靠 lib 目录按文件名排序让第三方 jar 优先加载**。新增依赖时必须意识到这个"按文件名字典序加载"的约定，随意改名可能引发 `NoSuchMethodError` 之类的运行时冲突。

## JSON / 日志 / 配置约定

- **JSON 三套并存**：fastjson（主）、org.json、gson。新代码沿用 fastjson；不要绕过 `setSafeMode` 的 autoType 限制。
- **日志统一 log4j2**（`resources/log4j2.xml`），logback 已排除，jcl/jul/slf4j/1.2-api 各桥都指向 log4j2。业务代码用 `commons/utils/LogUtil` 或 lombok `@Slf4j`。
- **配置走 profile**：`application.yml` 里 `spring.profiles.active: test`，另有 dev / prod；数据源、redis、xxl-job、mongodb shell 路径都在 profile yml 里，大量配置支持环境变量覆盖（`${TESTINPRO_DB_HOST:...}` 形式）。
