# 后台线程全景

> 网关并非无后台线程。Redis pub/sub 消息消费、用户活动异步记录都依赖后台线程池。本文梳理所有非请求线程的启动、配置与生命周期。

## 线程全景图

```
Boot.main() 启动
  │
  ├── DbConfigUtil.loadConfig()          ← 主线程
  │
  ├── MessageDispatchThread.start()      ← 单线程，持续运行
  │     └── BlockingPool.take() 阻塞等消息
  │
  ├── SubscribeFactory.subscribe()       ← 注册 Redis 订阅（内部有 listener 线程）
  │     ├── "real.cfg"    → McfgApp/McfgModule/McfgRole/McfgRoleApi 变更
  │     └── "usermanager" → UserOnline/User/Project/Enterprise 变更
  │
  └── SpringApplication.run()            ← 主线程 + Undertow I/O 线程
        │
        └── 请求处理线程（Undertow XNIO worker threads）
              │
              └── 特定场景会提交到:
                    ├── MessageHandlerThread 线程池 (5 核心/50 最大)
                    │     └── 处理每条 Redis pub/sub 消息
                    └── ThreadPoolUtil (固定 5 线程)
                          └── 异步写入用户活动
```

## MessageDispatchThread

`schedule/mq/MessageDispatchThread.java`

**类型**：单线程（`Thread` 子类），持续运行
**启动**：`Boot.main()` 中 `MessageDispatchThread.start()`（在 Spring 启动之前）
**生命周期**：JVM 进程生命周期（无优雅关闭）

**核心逻辑**：
```java
public void run() {
    while (!Thread.currentThread().isInterrupted()) {
        try {
            NoticeMessage msg = blockingPool.take();  // 阻塞等消息
            threadPool.submit(new MessageHandlerThread(msg));
        } catch (InterruptedException e) {
            break;
        }
    }
}
```

**关键点**：
- 从 `BlockingPool`（`LinkedBlockingQueue`）的 `take()` 阻塞拉取消息
- 拉取到消息后提交到线程池（核心 5 / 最大 50 / 无界队列）
- `BlockingPool` 由 `SubscribeFactory.getMessageListener()` 的消息回调填充

## MessageHandlerThread

`schedule/mq/MessageHandlerThread.java`

**类型**：`Runnable`，提交到上述线程池执行
**生命周期**：单条消息处理完即结束

**核心逻辑**：
```java
public void run() {
    messageService.Handler(message);
}
```

`MessageServiceImpl.Handler` 根据 `message.getTarget()` 路由到对应的 refresh/evict 方法（详见 [缓存与配置热更新](横切-缓存与配置热更新.md)）。

## ThreadPoolUtil

`web/util/ThreadPoolUtil.java`

**类型**：单例 `newFixedThreadPool(5)`
**用途**：用户活动异步记录（`UserActivityServiceImpl.addUserActivity`）
**生命周期**：静态初始化，JVM 进程生命周期

**使用方式**：
```java
ThreadPoolUtil.getInstance().submit(() -> {
    // 写到 V3 后端 /v3/user/user_activity/add_user_activity
    userActivityApi.addUserActivity(...);
});
```

**特点**：
- 固定 5 线程，无需弹性扩缩
- 适用于低频、无返回值的异步 fire-and-forget 任务
- 异常在 `UserActivityServiceImpl` 内部 try-catch，不会抛出到线程池

## Redis 订阅线程（SubscribeFactory 内部）

`SubscribeFactory` 来自 `real-common` 外部依赖，其内部实现：
- 通过 Jedis `subscribe()` 阻塞监听 Redis pub/sub
- 收到消息后填充 `BlockingPool`
- Jedis subscribe 是阻塞操作，订阅线程与 MessageDispatchThread 通过 BlockingPool 解耦

线程数：每频道一个订阅线程（`real.cfg` + `usermanager` = 2 个线程）

## 线程数汇总

| 线程/线程池 | 线程数 | 用途 |
|---|---|---|
| 主线程 | 1 | Boot.main() |
| Undertow I/O | 取决于 CPU 核数 | HTTP 请求处理 |
| Undertow Worker | 取决于配置 | HTTP 业务处理（servlet 执行） |
| Redis 订阅 | 2（每频道 1） | Redis pub/sub listen |
| MessageDispatchThread | 1 | 消息分发主线程 |
| MessageHandler 线程池 | 5 核心 / 50 最大 | 缓存刷新处理 |
| ThreadPoolUtil | 5 固定 | 用户活动异步写入 |

## 注意事项

1. **无优雅关闭**：`MessageDispatchThread` 的 while 循环没有与 Spring 生命周期绑定，`context.close()` 不会停止该线程。JVM 关闭时靠线程中断退出。
2. **BlockingPool 无界**：`LinkedBlockingQueue` 无容量限制，Redis pub/sub 消息堆积时可能导致 OOM。
3. **用户活动写入是 fire-and-forget**：失败不会影响主请求响应，但活动数据可能丢失。无重试机制。
