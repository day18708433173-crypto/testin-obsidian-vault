# 多版本入口（V1-V2-V3）

> 网关同时维护三个版本的 API 入口 Servlet，各自独立实现。本文对比三者的注册优先级、协议差异、鉴权差异、编排差异和转发模式判定。

## Servlet 注册

`cn/testin/startup/Boot.java`

```java
// Order(1) = 高优先级，先匹配
ServletRegistrationBean v2 = new ServletRegistrationBean(
    new ApiV2ProxyServlet(), "/v2/*", "/openapi/v2/*");
v2.setOrder(1);

ServletRegistrationBean v3 = new ServletRegistrationBean(
    new ApiV3ProxyServlet(), "/v3/*", "/openapi/v3/*");
v3.setOrder(1);

// Order(2) = 低优先级，兜底
ServletRegistrationBean v1 = new ServletRegistrationBean(
    new ApiProxyServlet(), "/*");
v1.setOrder(2);
```

**匹配优先级**：V2 `/v2/*` = V3 `/v3/*` > V1 `/*`。请求先被 V2/V3 截获，匹配失败的才落到 V1。

## 三版本差异总览

| 维度 | V1 (ApiProxyServlet) | V2 (ApiV2ProxyServlet) | V3 (ApiV3ProxyServlet) |
|---|---|---|---|
| URL 模式 | `/*` | `/v2/*`, `/openapi/v2/*` | `/v3/*`, `/openapi/v3/*` |
| 优先级 | `@Order(2)` 最低 | `@Order(1)` 高 | `@Order(1)` 高 |
| 协议风格 | JSON-RPC | REST URI 三段式 | RESTful 全方法 |
| 接口标识 | `action` + `op` (body) | URI: `/v2/{mkey}/{action}/{op}` | URI path + HTTP method |
| 认证方法 | `ApiUtil.commAuth` | `ApiV2Util.commAuth` | `ApiV3Util.commAuth` |
| IP 校验 | ✅ (appConfig.checkIp) | ❌ | ❌ |
| Timestamp 校验 | ✅ (12h, V1 only) | ❌ (已注释) | ❌ (已注释) |
| Hundsun 定制 | ✅ | ❌ | ❌ |
| sid 查询 | 所有接口都查 | 按 needLogin | 按 needLogin |
| checkKeys | ✅ | ✅ | ✅ |
| fieldKeys | ✅ | ✅ | ❌ |
| ignoreKeys (请求) | ✅ | ✅ | ❌ |
| additionalKeys | ✅ | ✅ | ✅ |
| resultCheckKeys | ✅ | ❌ | ❌ |
| queryParamKeys | ❌ | ❌ | ✅ |
| pathPlaceholderParamKeys | ❌ | ❌ | ✅ |
| bodyRequestFieldReplaceKeys | ❌ | ❌ | ✅ |
| responseFieldReplaceKeys | ❌ | ❌ | ✅ |
| passThroughType | ❌ (全部=0) | ❌ (全部=0) | ✅ (0 或 1) |
| HTTP 方法 | POST only | POST only | GET/POST/PUT/DELETE |
| multipart/form-data | ❌ | ❌ | ✅ (passThrough=1) |
| 文件下载 | ❌ | ❌ | ✅ (passThrough=1) |

## V1 协议细节

请求 body 格式：
```json
{
  "action": "app",
  "op": "Task.add",
  "apikey": "abc123...",
  "mkey": "realtest",
  "sid": "session_token",
  "data": {
    "field1": "value1"
  }
}
```

`action` 对应服务分类（app/script/file/device/plan/common...），`op` 对应具体方法（`Task.add`）。`mkey` 用于查 McfgModule 确定目标路由。

认证入口：`ApiUtil.commAuth`（`web/util/ApiUtil.java`）

## V2 协议细节

URI 格式：`/v2/{mkey}/{action}/{op}`

例：`POST /v2/realtest/app/Task.add`

`action`+`op` 从 URI 提取后注入到 body JSON，其他流程与 V1 基本一致。

认证入口：`ApiV2Util.commAuth`（`web/util/ApiV2Util.java`）

## V3 协议细节

URI 格式：`/v3/{mkey}/{resource_path}` + HTTP method

例：
- `GET /v3/user/users?pageSize=10&status=1`
- `POST /v3/realtest/task/create`
- `PUT /v3/realtest/task/stop_task`
- `DELETE /v3/script/scripts/123`

认证入口：`ApiV3Util.commAuth`（`web/util/ApiV3Util.java`）

### V3 两种转发子模式

| 子模式 | passThroughType | 判定条件 | 代码路径 |
|---|---|---|---|
| V3 透传 | 1 | `McfgApi.protocolConfig.passThroughType == 1` | `doPressWithPassThrough()` |
| V3→V1 转换 | 0 | `passThroughType == 0` + `specialApiAction/Op` 非空 | `executeRequest()` |

详细分析见 [V3透传](核心链路-V3透传.md) 和 [V3→V1转换](核心链路-V3转V1.md)。

## 编排差异关键点

V3 不在请求前阶段执行 `fieldKeys` 和 `ignoreKeys`（请求 body 黑/白名单），只在响应后执行 `ignoreKeys`。原因是 V3 的请求 body 由前端构造，结构不可控，不适合直接过滤。

V3 独有的 `queryParamKeys`、`pathPlaceholderParamKeys`、`bodyRequestFieldReplaceKeys`、`responseFieldReplaceKeys` 是 RESTful 风格的配套能力。

## 转发模式判定差异

| 版本 | RPC 判定 | HTTP 判定 | 透传判定 |
|---|---|---|---|
| V1/V2 | `httpHosts` 为空 | `httpHosts` 非空 | 无 |
| V3 | `httpHosts` 为空 + passThroughType=0 | `httpHosts` 非空 + passThroughType=0 | passThroughType=1 + `httpHosts` 非空 |

V3 的 `passThroughType` 是第二维度判定，与 `httpHosts` 是否存在组成 2×2 矩阵，但当前代码中 passThroughType=1 时必须 httpHosts 存在（否则透传无意义）。
