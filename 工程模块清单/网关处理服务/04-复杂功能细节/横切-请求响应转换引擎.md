# 请求响应转换引擎

> 网关的核心价值之一是"请求编排"：在转发前/响应后对 JSON 做声明式转换，规则由 McfgApi.protocolConfig 驱动。本文详解所有编排配置项的格式、代码路径和版本兼容性。

## 编排配置全景

```
请求到达
  │
  ├── [请求前] checkKeys ─────────── 必填字段校验
  ├── [请求前] fieldKeys ─────────── 白名单过滤（仅 V1/V2）
  ├── [请求前] ignoreKeys ────────── 黑名单裁剪
  ├── [请求前] additionalKeys ────── 字段注入（含占位符替换）
  ├── [请求前] V3: queryParamKeys ─── query→body 映射
  ├── [请求前] V3: pathPlaceholderParamKeys ── 路径→body 映射
  ├── [请求前] V3: bodyRequestFieldReplaceKeys ── body 字段重命名
  │
  ▼ 转发到目标服务
  │
  ├── [响应后] V1: resultCheckKeys ──── 响应 projectid 校验
  ├── [响应后] V3: responseFieldReplaceKeys ── 响应字段重命名
  ├── [响应后] ignoreKeys ────────── 响应黑名单裁剪
  └── [响应后] fieldKeys ─────────── 响应白名单过滤（仅 V1/V2）
```

## checkKeys — 必填字段校验

**适用版本**：V1 / V2 / V3
**执行阶段**：请求前（`commAuth` 之后，`preExecuteRequest` 之前）

**代码**：`ApiProxyServlet.handleCheck(ApiRequest, McfgApi)`

**格式**：
```json
{
  "checkKeys": ["field1", "nested.field2", "array[].field3"]
}
```

**逻辑**：
1. 遍历 `checkKeys` 中的每个 key
2. 按 `.` 分割 key 路径，逐层深入 data JSON
3. 任一 key 缺失或值为 null → 抛出 `GeneralException(paraInvalid, "缺少必填项: " + key)`

**坑**：`checkKeys` 的格式必须与 protocolConfig 的约定一致，格式错误会导致 `configInvalid`。

## fieldKeys — 白名单过滤

**适用版本**：V1 / V2（V3 未实现）
**执行阶段**：请求前 / 响应后

**代码**：`ApiProxyServlet.handleField(JSONObject, McfgApi)`

**格式**：
```json
{
  "fieldKeys": ["keepField1", "keepField2", "nested.keepField3"]
}
```

**逻辑**：
1. 创建新的空 JSONObject
2. 遍历 `fieldKeys`，从原始 data 中取值，写入新对象
3. 支持嵌套路径（`.` 分割）和数组（递归对每个元素执行 fieldKeys）

**与 ignoreKeys 的关系**：fieldKeys 优先级高于 ignoreKeys。如果两者同时存在，只有 fieldKeys 生效。

## ignoreKeys — 黑名单裁剪

**适用版本**：V1 / V2（请求前+响应后）/ V3（仅响应后）
**执行阶段**：请求前 / 响应后

**代码**：`ApiProxyServlet.handleIgnore(JSONObject, McfgApi)`

**格式**：
```json
{
  "ignoreKeys": ["removeField1", "removeField2", "nested.removeField3"]
}
```

**逻辑**：
1. 遍历 `ignoreKeys`，从 JSON 中递归移除指定 key
2. 支持嵌套路径（`.` 分割）
3. 在 `preExecuteRequest` 阶段处理请求 body，在 `postDealResponse` 阶段处理响应 body

## additionalKeys — 字段注入

**适用版本**：V1 / V2 / V3
**执行阶段**：请求前（`preExecuteRequest`）

**代码**：`ApiProxyServlet.handleAdditional(JSONObject, McfgApi, McfgApp)`

**格式**：
```json
{
  "additionalKeys": {
    "field1": "staticValue",
    "field2": "${app.bindEid}",
    "field3": "${app.appName}",
    "nested": {
      "innerField": "value"
    }
  }
}
```

**逻辑**：
1. 深度合并 `additionalKeys` 到请求 data
2. 字符串值中的 `${app.bindEid}` 替换为 `McfgApp.bindEid`
3. 字符串值中的 `${app.appName}` 替换为 `McfgApp.appName`
4. 嵌套对象递归合并

## resultCheckKeys — 响应字段校验（V1 独有）

**适用版本**：仅 V1
**执行阶段**：响应后（`postDealResponse`）

**代码**：`ApiProxyServlet.handleCheckResult(ApiRequest, JSONObject, IUserService)`

**格式**：
```json
{
  "resultCheckKeys": {
    "projectid": "userProjectIds"
  }
}
```

**逻辑**：
1. 从响应 data 中取 `projectid` 的值
2. 从用户项目列表中查找该 projectid
3. 不在列表内 → 抛出 `GeneralException(paraProjectidInvalid)`

典型用途：确保响应数据属于当前用户有权访问的项目。

## V3 独有编排配置

### queryParamKeys — Query→Body 映射

**适用版本**：仅 V3
**执行阶段**：请求前（`preExecuteRequest`）

**代码**：`ApiV3ProxyServlet.transformToDataJson(ApiV3Request)`

**格式**：
```json
{
  "queryParamKeys": {
    "pageSize": "page.size",
    "status": "filter.status",
    "appId": "appId"
  }
}
```

**逻辑**：
1. 遍历 `queryParamKeys` 中的每个映射
2. 从 `request.getParameter(key)` 取值
3. 按映射的目标路径（`.` 分割）写入 body JSON
4. 类型转换支持：
   - `Integer`：`Integer.parseInt(value)`
   - `Long`：`Long.parseLong(value)`
   - `Boolean`：`Boolean.parseBoolean(value)`
   - 默认：字符串

### pathPlaceholderParamKeys — 路径占位符→Body 映射

**适用版本**：仅 V3
**执行阶段**：请求前（`preExecuteRequest`）

**代码**：内联在 `ApiV3ProxyServlet.preExecuteRequest`

**格式**：
```json
{
  "pathPlaceholderParamKeys": {
    "param0": "userId",
    "param1": "projectId"
  }
}
```

示例：请求 `/v3/user/users/123/projects/456`，提取 param0="123", param1="456" → body: `{"userId": "123", "projectId": "456"}`

### bodyRequestFieldReplaceKeys — Body 字段重命名

**适用版本**：仅 V3
**执行阶段**：请求前（`preExecuteRequest`）

**代码**：`ApiV3ProxyServlet` 递归方法:380-410

**格式**：
```json
{
  "bodyRequestFieldReplaceKeys": {
    "camelCaseField": "snake_case_field",
    "appId": "app_id"
  }
}
```

**逻辑**：递归遍历 body JSON 的所有 key，将匹配的 key 替换为目标名。支持嵌套对象和数组内的对象。

### responseFieldReplaceKeys — 响应字段重命名

**适用版本**：仅 V3
**执行阶段**：响应后（`getResponseResult`）

**代码**：`ApiV3ProxyServlet` 递归方法:430-460

**格式**：同 bodyRequestFieldReplaceKeys，但应用于响应 JSON。

典型用途：将后端返回的非驼峰字段转为前端期望的驼峰格式。

## ignoreSidKeys — 控制用户信息注入

**适用版本**：V1 / V2 / V3
**执行阶段**：请求前（`preExecuteRequest` / `addBaseInfoToBody`）

**格式**：
```json
{
  "ignoreSidKeys": {
    "infoBySid": 1
  }
}
```

当 `infoBySid=1` 时，即使全局 ignoreSid 未开启，该接口也跳过 sid 用户信息注入。

**ignoreSid 三层控制**（优先级从高到低）：
1. API 级：`ignoreSidKeys.infoBySid=1`
2. mkey 级：`prodatatrans` / `saasdatatrans` 硬编码
3. App 级：`appConfig.ignoreSid=1`
