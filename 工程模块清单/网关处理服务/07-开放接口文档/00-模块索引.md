# 开放接口文档索引

> 网关处理服务本身不提供业务接口，以下为 4 个 Servlet 入口的认证流程与代理转发规则说明。

## Servlet 一览

| Servlet | URL 映射 | 说明 |
|---|---|---|
| ApiProxyServlet | `/*` | V1 网关，JSON action/op 模式，处理所有未匹配到 /v2/* 和 /v3/* 的请求 |
| ApiV2ProxyServlet | `/v2/*` | V2 网关，RESTful URI 模式 `/v2/{mkey}/{action}/{op}` |
| ApiV3ProxyServlet | `/v3/*`, `/openapi/v3/*` | V3 网关，RESTful 全方法（GET/POST/PUT/DELETE），支持 placeholder URL、query→body、multipart |
| LocalCacheServlet | `/localcache/*` | 缓存管理，`?key=xxx` 清除指定 LocalCache 条目 |

## 通用认证流程

所有外部请求经网关时需通过以下认证链（V1 在 `ApiUtil.commAuth`，V3 在 `ApiV3Util.commAuth`）：

```
1. 参数校验
   ├── apikey    → 必填，应用身份标识
   ├── mkey      → 必填，目标模块标识
   ├── action    → V1/V2 必填，接口包名
   ├── op        → V1/V2 必填，接口方法名
   ├── timestamp → AppConfig.checkTimestamp=1 时必填
   └── sid       → needLogin=1 时必填或从 Cookie authtoken_pro 获取

2. 应用校验（McfgApp）
   ├── apiKey 有效性 → McfgApp.status=1（启用）
   ├── roles 非空 → 至少有 1 个角色
   ├── bindEid 非空 → 已绑定企业
   └── IP 白名单 → AppConfig.checkIp=1 时校验

3. 模块校验（McfgModule）
   └── mkey 有效性 → McfgModule.status=1（启用）

4. 接口权限校验（McfgApi）
   ├── action+op 匹配 → McfgApi.status=1
   └── needLogin → 需要时校验 sid 登录态

5. 用户校验（如 needLogin=1）
   ├── sid → UserOnline（含 eid/email/userid/name）
   ├── eid 与 McfgApp.bindEid 一致性
   └── projectid 与用户项目列表一致性（如请求含 projectid）
```

## V1 请求格式（ApiProxyServlet）

V1 使用 JSON body 的 action/op 模式：

```json
{
  "mkey": "script",
  "action": "script",
  "op": "ScriptList.get",
  "apikey": "abc123...",
  "sid": "session_id",
  "timestamp": 1234567890,
  "sig": "md5_signature",
  "data": {
    "projectid": 1,
    "...": "..."
  }
}
```

**代理转发逻辑**（`ApiProxyServlet.executeRequest`）：

1. 从 request attribute 获取 `McfgModule`
2. `module.getHttpHosts()` 为空 → RPC 模式：`irpcservice.doPress(module.getRpcPrefixName(), sendJson)`
3. `module.getHttpHosts()` 不为空 → HTTP 模式：`ihttpservice.doPress(request, httpHost, sendJson)`

**响应处理**：与请求编排对称，依次执行 `handleResultCheckJson` → `handleIgnoreJson` → `handleFieldJson`。

## V2 请求格式（ApiV2ProxyServlet）

V2 将 action/op 编码在 URL 中：

```
POST /v2/{mkey}/{action}/{op}
```

Body 直接为 data JSON，不需要 action/op/mkey/sid/apikey 等字段。网关从 URL 提取后重新组装标准 V1 格式的 sendJson 再转发。

## V3 请求格式（ApiV3ProxyServlet）

V3 支持标准 RESTful：

```
GET    /v3/{mkey}/resource?project_id=1&page_size=10
POST   /v3/{mkey}/resource
PUT    /v3/{mkey}/resource/{id}
DELETE /v3/{mkey}/resource/{id}
```

### V3 独有特性

**Placeholder URL**：URL 中的 `{id}` 等路径变量可配置 `pathPlaceholderParamKeys` 映射到 body JSON 字段。

**Query → Body 转换**：URL query 参数可通过 `queryParamKeys` 转换为 body JSON，支持类型转换（Integer/Long/Boolean）和嵌套路径（如 `condition.keywords`）。

**Pass-Through 模式**：`passThroughType=1` 时，请求直接透传到目标服务，不进行 V1 风格的 body 组装。

**Body 字段替换**：`bodyRequestFieldReplaceKeys` 在请求前将驼峰字段转为目标格式；`responseFieldReplaceKeys` 在响应后将非驼峰字段转为驼峰。

**响应直通**：支持 `Content-Type: application/octet-stream` 和 `Set-Cookie` 的透传。

## 签名算法（SigUtil）

当 `AppConfig.checkSig=1` 时需传递 `sig` 参数：

1. 取请求 JSON 的所有 key，按字母序排列
2. 跳过 `sig` 字段
3. 递归拼接 `key=value`（嵌套 JSONObject/JSONArray 递归排序）
4. 末尾追加 `secretKey`（来自 McfgApp）
5. MD5 哈希得到 sig

```
sig = MD5(key1=value1key2=value2...secretKey)
```
