# 内部工具与脚本重建

> 文件管理服务除了对外上传/解析/校验，还带一批**面向内部运维的旁路工具**：文件删除、磁盘清理、包记录删除、keystore 更新、健康检查，以及一条专门用来**修复脚本步骤数据**的脚本重建链路。这些不是高频主链路，但出了问题要靠它们兜底。代码级细节见 [脚本重建实现](../03-实现逻辑/脚本重建实现.md)。

## 内部工具清单

| 工具 | 端点 | 作用 |
|---|---|---|
| 文件删除 | `/operation/delete`（`OperationController`） | 手动删除文件，本地 + 远程存储一并清理 |
| 磁盘清理 | `/clean/disk`（`CleanResultController`） | 清理本地磁盘占用 |
| 包记录删除 | `/package/delete/record`（`PackageController`） | 删除 App 版本包记录 |
| keystore 更新 | `/app/update/keystore`（`AppController`） | 更新应用签名 keystore |
| 健康检查 | `/heartbeat/check`（`HeartBeatController`） | 试上传一个 txt 验证存储通路是否可用 |
| 脚本批量重检 | `/api/checkScript` 系列（`ApiController`） | 内部触发脚本校验（见 [脚本校验](脚本校验.md)） |

其中文件删除不是单一入口：除 `/operation/delete` 手动删除外，还有多个后台 worker 在做定时/按队列的清理（清理超期文件、从 Redis SET 取 URL 删除、清理过期结果文件），详见 [横切-后台线程全景](../04-复杂功能细节/横切-后台线程全景.md)。

## 脚本重建：修数据而不是重传

脚本重建解决的是"程序造成的脚本步骤不完整、历史属性不满足最新需求"这类数据问题——不要求用户重新上传脚本，而是**拿脚本 ZIP 的内容把 `script_step` 补齐/修正**。

入口是 `POST /rebuild/scriptStep`（`RebuildController.scriptStep`），用户给定 `projectId`、`sid`、起止时间 `start`/`end`（13 位时间戳），可选 `ignoreScriptList`（忽略的脚本 id 列表）和 `process_cycle`（默认 30）：

- 按 projectId + 时间范围查出待重建的脚本列表（可排除忽略列表）；
- 逐个下载脚本 ZIP → 解压 → 从 ZIP 里取出 `TestCase`（步骤定义）；
- 拿 ZIP 里的步骤和库里 `script_step` 对照，分三种情况处理：

| 情况 | 判断 | 处理 |
|---|---|---|
| 库表无步骤 | `script_step` 为空 | 全量插入步骤 |
| 步骤不完整 | 库表步骤数 < ZIP 里 `actions` 条数 | 逐条补缺失步骤，并补期望图片、子脚本引用、ext/stepname 等属性 |
| 步骤齐全但缺 ext | 库表步骤数 == actions 条数 | 只逐条补 `ext` 字段 |

两个关键原则：

1. **只补不改、不清理**：代码明确"不清理所有脚本步骤，只处理缺失属性和步骤不全的记录"，不会删掉已有步骤；
2. **子脚本引用回填**：步骤里 `call` 类型的调用，若 `childScriptNo` 为空，会解析被调脚本名回填脚本编号，并按 projectId 查最新脚本回填 `childScriptId`。

注意一个文案小坑：入口代码里报错文案写"重建资源周期不能超过1周"，但 `process_cycle` 默认值是 30，实际默认允许 30 天的跨度——文案与实际默认值不一致。
