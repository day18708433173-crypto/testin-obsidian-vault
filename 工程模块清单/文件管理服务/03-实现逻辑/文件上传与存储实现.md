# 文件上传与存储实现

> 本文补齐除 APP 解析链、脚本校验引擎之外的另一条主线：**文件实体如何进平台、如何落到存储后端**。覆盖 V1 原生 `fs.*` 上传、V3 `/file_system` 上传、token 鉴权签发与校验、FastDFS/MinIO 存储后端选择。端点级出入参见 [09-文件管理服务 openapi 汇总](../../网关处理服务/07-开放接口文档/openapi/09-文件管理服务.md)，存储专题见 [横切-存储后端](../04-复杂功能细节/横切-存储后端.md)，鉴权专题见 [横切-上传鉴权体系](../04-复杂功能细节/横切-上传鉴权体系.md)。

## 双入口总览

文件管理服务对外接收文件实体有两个独立入口体系，最终都汇到 `IFileUploadService` 存储接口：

| 入口体系 | 入口类 | 路由 | 说明 |
|---|---|---|---|
| V1 原生（action/op 反射） | `cn.testin.service.fs.File` | `action=fs&op=File.upload` 等 | 网关 mkey=`fs`（pass_through_type=0），流式 / multipart / 分片合并 |
| V3 透传（Spring MVC） | `AppV3Controller` / `FileUploadV3Controller` | `/file_system/app/upload`、`/file_system/files/upload` | 网关 mkey=`file_system`（pass_through_type=1），仅这两条在网关注册 |
| V3 未注册端点 | `FileUploadController` / `AppUploadController` 等 | `/file/upload-app`、`/app/checkChunk` 等 | 代码内 Spring MVC 端点，未在 db_mcfg 注册，详见 07 接口文档 |

## 一、V1 原生 `fs.File` 上传

入口类 `cn.testin.service.fs.File`（extends `GenericBaseService`），由 ApiServlet 经 `action=fs` 反射调用，业务对象从 `apirequest.getReqjson()` 取参。

### File.upload — 流式上传

`File.upload` 直接消费 `request.getInputStream()` 文件二进制流：

1. 从 reqjson 取 `suffix`（必填，空则返回 paraInvalid）、`fileName`、`fileType`、`directUpload`（默认 NOT_DIRECT_UPLOAD）；
2. `FileUploadServiceFactory.fileUploadService.upload(inputStream, fileName, suffix, fileType, directUpload)` 落存储；
3. 返回 `data.result` = 文件 URL（`ApiUtil.getJSONobj` 组装）。

### File.multipartUpload — form 分片/非分片

`File.multipartUpload` 用 `CustomerMultipartResolver` 解析 multipart 请求，按 `chunk`（0/1）分流：

- `chunk=1`（分片模式）：`fileMark` 必填（唯一标记），分片落临时目录 `fileMark` 子目录，返回 `data.result=1`；
- `chunk=0`（非分片）：`suffix` 必填，逐文件 `up(tempFile, suffix, chunk)` 直传存储，返回 `data.result` = URL 列表。

### File.merge — 分片合并（异步队列）

`File.merge` 不直接合并，而是把合并任务投递给 `FileMergeUtils`：

1. `key = fileMark + "_" + suffix`；若 `FileMergeUtils.getFileMergeMap()` 已有结果直接返回，否则构造 `FileMergeData`（code=WAITING）放入 map；
2. `FileMergeUtils.getFileMergeQueue().offer(fileMergeData)` 投递合并队列，`FileMergeThread`（后台线程）消费后真正合并并上传；
3. 返回 `data.objInfo` = `FileMergeData`（code/msg/fileMark/suffix/fileName/url/md5Key/fileType），`data.result` 取 `fileMergeData.getUrl()`（合并完成前为空）。

> 合并的底层实现在 `FastDFSFileUploadServiceImpl.merge` / `MinioFileUploadServiceImpl.merge`：按分片文件名数字排序后用 `FileChannel.transferTo` 逐片拼接，再上传并删除分片目录。注意这是 V1 `File.merge` 的异步合并队列，与 V3 `AppUploadController.mergeChunk` 的同步合并是两套独立实现（后者见 [核心链路-分片上传](../04-复杂功能细节/核心链路-分片上传.md)）。

## 二、V3 `/file_system` 上传

### AppV3Controller.uploadApp — APP 上传（fileUrl / file 双模式）

`AppV3Controller.uploadApp`（类级 `@RequestMapping("/file_system")`，方法 `/app/upload`）：

1. `AuthApi.getUserOnline(sId)` 换 userId（失败返回 "sid is invalid"）；`eId`/`projectId`/userId 任一为空即失败；
2. `fileUrl` 与 multipart `file` 必须二选一（都空返回 "fileUrl、file is null"）；
3. 置 `bizCode=parseApp`、`from="/V3"`（`/V3` 标记使后续 `AppFileProcessor.checkAppAndSuite` 跳过"已绑定应用"校验）；
4. `uploadToHD` 分流：`fileUrl` 走 `transferUrlStreamToHD`（远程下载），`file` 走 `transferSpringRequestStreamToHD`（multipart 落盘）；
5. `AppExtEnum.has(originalExtName)` 白名单校验，不通过返回"该接口只接受…格式的文件"；
6. `processsFacade` 进责任链，与 `/file/upload-app` 共用 `AppFileProcessor` 解析入库（见 [App包上传与解析实现](App包上传与解析实现.md)）。

### FileUploadV3Controller.filesUpload — 通用文件上传

`FileUploadV3Controller.filesUpload`（`/file_system/files/upload`）：直接调 `FileUploadServiceFactory.fileUploadService.multipartUpload(multipartFiles, false, null, suffix, fileType)`，多文件逐个上传，返回 `data.result` = URL 列表。**不走责任链、不解析**，是最纯粹的"存文件拿 URL"。

### ScriptV3Controller.scriptStatusSync — 脚本状态同步

`ScriptV3Controller.scriptStatusSync`（`/script/status/sync`）：接收 `List<ScriptCheckStatusSync>` 回写脚本校验状态同步队列，供后台 `SyncScriptNoStatusThread` 同步用例侧。

## 三、Token 签发与校验

token 鉴权是给第三方业务服务（如自动打包流水线）用的开放上传凭证，分"签发"与"校验"两端。

### 签发端 TokenController

- `TokenController.get`（`GET /token/get`，参数 `serivceId`、`publicKey`）：
  1. 查 `upload_service_auth` 表确认 `serivceId` 已注册；
  2. 校验 `publicKey == MD5(serivceId + privateKey)`（privateKey 为注册时下发的私钥）；
  3. 生成 `access_token = UUID`，写入 Redis `fileUpload_{serivceId}`，TTL `DEFAULT_EXPIRES = 7200` 秒（2 小时）。
- `TokenController.registerService`（`POST /token/registerService`，参数 `serviceName`）：`privateKey = Base64(timestamp).substring(1,10)`，写入 `upload_service_auth` 表并返回私钥。

### 校验端 UploadFileRequest

`UploadFileRequest.parseHttpRequest(request, needSid, needAccessToken)` 在 `needAccessToken=true` 时：

1. 从 UPLOAD-JSON 取 `serviceId`、`accessToken`，任一为空即失败；
2. `UploadAuthService.get` 查 `upload_service_auth` 确认 serviceId 已注册；
3. `StringRedisTemplate` 查 `fileUpload_{serviceId}`：key 不存在 → "accessToken is expired"；`accessToken` 不等于 Redis 值 → "accessToken is invalid"。

**重要**：校验逻辑入口 `parseHttpRequestWithToken`（即 `parseHttpRequest(request, false, true)`）当前**无任何调用方**——`HttpStreamUpload` 用 `parseHttpRequest(request)`（needSid=false, needAccessToken=false）、`OpenUpload` 用 `parseHttpRequest(request, true, false)`（只验 sid 不验 token）。即 token 的签发接口与校验代码都在，但本分支没有任何上传端点实际启用 needAccessToken，token 机制处于"定义完备、未接线"状态。

## 四、存储后端选择（FastDFS / MinIO 二选一）

存储统一收口在 `IFileUploadService`，工厂做部署期二选一，非运行时兜底：

```
FileUploadServiceFactory.getInstance()
  └─ Config.MINIO_USABLE == true
       ├─ true  → Spring bean "minioUploadService"（MinioFileUploadServiceImpl）
       └─ false → Spring bean "fastDFSFileUploadService"（FastDFSFileUploadServiceImpl）
```

- `fileUploadService` 是**静态字段**，首次 `getInstance()` 后进程内不再切换（`FileUploadServiceFactory.java`）。`afterPropertiesSet()` 在启动时即触发一次初始化。
- `Config.MINIO_USABLE` 优先读环境变量 `MINIO_USABLE`，其次 `config.properties` 的 `minio.usable`。

两个实现类对 `IFileUploadService` 的行为差异：

| 能力 | FastDFSFileUploadServiceImpl | MinioFileUploadServiceImpl |
|---|---|---|
| 上传底层 | `FastDFSService.upload`：≤10M 走 `upload_file1`，>10M 走 `uploadFileByChunk`（10M 一块断点续传） | `MinioService.upload`：S3 桶+objectName |
| 流式上传 directUpload | `upLoadFileToRemoteByStream`（字节流直传） | 同左 |
| 分片合并 | `merge` 按数字排序 FileChannel 拼接 | 同左（注释"fastDfs中有分片合并上传,minio不需要"实为历史注释，`merge` 仍实现） |
| 删除远程 | 正则匹配 `group/M00/..` 提取 group + remote_filename 后 `FastDFSService.deleteRemoteFile` | 正则匹配 `bucketName/objectName` 后 `MinioService.delete` |
| 对外 URL | `Config.getPublicFileBaseUrl() + fileId`，带 fileName 时拼 `?filename=xx.suffix` | 同左 |

URL 拼接统一规则：`Config.getPublicFileBaseUrl()`（MinIO 用 `MINIO_BASE_URL`，FastDFS 用 `TRACKER_SERVICE_PATH`）+ 存储返回的 fileId/objectName；原始文件名非空时追加 `?filename=`。

## 注意事项与坑

1. **token 机制未接线**：`parseHttpRequestWithToken` 当前无调用方，`/token/get` 签发的 token 不会被任何上传端点消费；不要误以为第三方上传已受 token 保护。
2. **存储后端静态缓存**：`FileUploadServiceFactory.fileUploadService` 首次初始化后进程内固定，FastDFS 挂掉不会落到 MinIO，不要按主备理解（同 [App包上传与解析实现](App包上传与解析实现.md) 的坑 1）。
3. **V1 `File.merge` 是异步的**：返回的 `data.result` 在合并完成前为空，调用方需轮询 `FileMergeData.url`；与 V3 `AppUploadController.mergeChunk` 的同步合并不是同一套代码。
4. **`FileUploadV3Controller.filesUpload` 直接读静态字段** `FileUploadServiceFactory.fileUploadService`（非 `getInstance()`），依赖启动时 `afterPropertiesSet()` 已初始化，冷启动顺序异常时可能 NPE。
