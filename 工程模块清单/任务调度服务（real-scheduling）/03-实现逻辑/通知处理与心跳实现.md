# 通知处理与心跳实现

## 概述

本文覆盖任务调度服务的两条"后台基建"链路：**可靠通知处理**（`mq_info_notice` 表 + MQ 消费，8 类通知）与**心跳健康检查**（`HeartBeatController` 三存储探活）。前者是取消/回收/撤销/激活/上报等异步动作的统一载体，后者是存活探针。

## 一、可靠通知处理（MQ）

### 线程框架

`StartRunner`（`real-scheduling/src/main/java/cn/testin/config/StartRunner.java`）启动后：

1. **MqNoticeDataThread**（200ms 周期）从 `mq_info_notice` 表把 8 类待处理通知装入内存队列（`INoticeService.jobqueue("scheduling")`）；
2. **NoticeDispatchThread** 从内存队列取通知分发（构造参数 `new NoticeDispatchThread(inoticeservice, jobqueue("scheduling"), 100, 10, 100)`，见 `StartRunner.java`）；
3. 消费主体是 `NoticeServiceImpl.handle`（`real-scheduling/src/main/java/cn/testin/business/impl/NoticeServiceImpl.java`，extends AbstractNoticeServiceImpl），按 `type` 路由到 8 个 handler。

### 8 类通知

| type | 枚举 | handler | 作用 |
|---|---|---|---|
| 0 | cancelTask | handleCancelTask | 取消任务：`ITaskService.cancel(taskid, subtaskid, crossTaskid, taskGroup)` |
| 1 | recoverTask | handleRecoverTask | 设备回收：按 deviceid（APP，含 `@` 判定为 Web ucomid）/pcId 分发 `recover` |
| 2 | releaseAccount | handleReleaseAccount | 释放账号：`AccountApi.release` 调 app处理服务 |
| 3 | stopDeviceTask | handleStopDeviceTask | 停止设备任务：`TaskApi.stop` 调设备控制中心 |
| 4 | actionReport | handleActionReport | 动作上报：`ITestProcessService.report(action, taskid, subtaskid, contentmap)`（INIT/MATCH 等激活链路） |
| 5 | revokeTask | handleRevokeTask | 撤销设备任务：逐台 `cancel(..., DEVICEEXPIRE)` |
| 6 | crossReport | handleCrossReport | 跨端结果回传多端中心（`NoticeReportApi.report`，见 [跨端任务实现](跨端任务实现.md)） |
| 7 | scriptExecute | handleScriptExecute | 激活待调度任务：`ITaskService.execute(taskId, projectId)` |

枚举见 `TaskConfigEnum.NoticeType`（`real-scheduling/src/main/java/cn/testin/pojo/task/TaskConfigEnum.java`），每种 `validPeriod=1h`、`delaytime=0`、`level=0`。

### 重试与终态策略

`NoticeServiceImpl.handle` 的 finally 块（`NoticeServiceImpl.java`）统一结算：

- **成功**：`exec_num+1`，状态置 `STATUS_FINISH`；
- **失败**：`exec_num+1`；`exec_num >= 3` 时把 `publishtime` 推迟 10 秒再试；`exec_num > 10` 且创建超过 1 小时 → 置 `STATUS_INVALID`（判死）；
- **非法**（handler 返回 INVALID，如参数缺失）：`exec_num+1` 并直接置 `STATUS_INVALID`。

### 动作上报消费链 handleActionReport

`handleActionReport` 解析 content 里的 `taskaction/taskid/subtaskid`，其余字段塞进 `contentmap`，转调 `ITestProcessService.report(action, taskid, subtaskid, contentmap)`。这是任务初始化激活（INIT）、匹配上报（MATCH）等动作的统一入口——`TaskAction` 枚举含 `init/prematch/match/running/preComplete/report/complete/recover/cancel/expire/execNumError`（`TaskConfigEnum.TaskAction`）。

## 二、心跳健康检查

`HeartBeatController#check`（`real-scheduling/src/main/java/cn/testin/controller/HeartBeatController.java`，`GET /v3/realscheduling/heartbeat/check`）对三个存储做轻量探活：

- `HeartBeatCheckRedisDAO.heartbeatCheck`：Redis PING；
- `HeartBeatCheckMysqlDAO.heartbeatCheck`：MySQL 查询（db_task 库）；
- `HeartBeatCheckEsDAO.heartbeatCheck`：ES cluster health。

三者全部通过返回 `ResponseResult.success`；任一失败抛 `HealthyCheckGenericException`，被 `@ExceptionHandler` 捕获返回 HTTP 500。详见 [HeartBeatController 接口文档](../07-开放接口文档/基础设施/HeartBeatController.md)。

| 表 | 本链路操作 |

| mq_info_notice | 8 类通知载体：MqNoticeDataThread SELECT、handle 后 UPDATE status/exec_num |
| task_info / task_sub_info | 各 handler 的取消/回收/激活等 UPDATE |

## 注意事项与坑

1. **通知可靠但最终可能判死**：失败重试 3 次后推迟 10s、超过 10 次且超 1 小时置 INVALID——极端故障下通知会"放弃"，需人工排查 INVALID 记录。
2. **8 类通知是白名单**：`StartRunner` 只订阅这 8 个 type；`NoticeServiceImpl.handle` 对未知 type 不处理也不置终态。
3. **心跳不探业务**：`/heartbeat/check` 只探三存储连通性，不验证任务调度逻辑本身是否健康，不能替代业务监控。
