# 异常恢复

> 任务调度服务要保证"任务不会永远挂着"：取消、过期、匹配超限、设备离线、设备异常等场景都要把任务收尾成 `task_result` 并清理三链数据。本文汇总各异常场景的触发源、处理路径与兜底。

## 异常场景全景

| 场景 | 触发源 | 处理路径 | 结果码 |
|---|---|---|---|
| 用户取消 | `Task.cancel` → MQ `cancelTask` | `NoticeServiceImpl.handleCancelTask` → `ITaskService.cancel` | CANCEL 888888 |
| 设备回收 | `Task.recover` → MQ `recoverTask` | `handleRecoverTask` → `recover` 置回待执行 | 无（重新匹配） |
| 设备撤销 | `Task.revoke` / 异常设备到期 → MQ `revokeTask` | `handleRevokeTask` → 逐台 `cancel(DEVICEEXPIRE)` | DEVICEEXPIRE 999998 |
| 停止设备任务 | MQ `stopDeviceTask` | `handleStopDeviceTask` → `TaskApi.stop` | 无 |
| 过期 | `TaskDispatchThread` 扫描 | `ResultServiceImpl.handleAbnormalTask` | EXPIRE 999999 |
| 匹配超限 | 同上（execNum>10 或 =10 且 IDLE） | `handleAbnormalTask` | EXECERROR 666666 / WEBEXECERROR 666667 / DEVICEEXCEPTION 999997 |
| 设备离线跳过 | `TaskDeviceCheckThread`（5 分钟） | `ResultServiceImpl.handleSkipTask` | SKIP 444444 |
| 释放账号 | MQ `releaseAccount` | `handleReleaseAccount` → `AccountApi.release` | 无 |

## 核心收尾：handleAbnormalTask

`ResultServiceImpl.handleAbnormalTask`（`real-scheduling/src/main/java/cn/testin/business/impl/ResultServiceImpl.java`）是取消/过期/超限三类异常的统一收尾：

1. 校验 `execStatus/execNum/expiretime` 非空；
2. 判定异常：`execStatus==CANCEL`；或 `expiretime < now`（置 reportCross）；或 `execNum > 10` 或（`execNum==10 且 IDLE`）；
3. 非异常直接抛 `paraInvalid`（防御：只处理确属异常的）；
4. 多端 RETENTION 任务且过期：先 `NoticeReportApi.report` 上报 EXPIRE 给多端中心；
5. `taskinfoRunningNoticeUCom` 通知上位机停止；对 `taskAction:subtaskid` 加锁；
6. 遍历未完成子子任务（跳过 FINISH），按场景写 `task_result`（见 [任务状态机](任务状态机.md) 结果码表）；
7. `callComplete("Abnormal")` 回调、删 task_sub_info / EsTaskInfo / task_info；task_info 表该 taskid 无数据时再删 task_info_extra、时间段、脚本设备聚焦。

## 设备离线跳过：handleSkipTask

`ResultServiceImpl.handleSkipTask`（`ResultServiceImpl.java`）只处理 `execStatus==SKIP` 的子子任务：对 `taskAction:subsubtaskid` 加锁，查 task_info、确认无已存在结果后，写一条 `result_code=SKIP(444444)` 的 task_result。触发方是 `TaskDeviceCheckThread`（@Scheduled 5 分钟），对 `deviceOfflineConfig=2` 的任务、可执行设备全部离线时把子子任务置 SKIP。

## 匹配耗尽策略

匹配次数上限 `TASK_MAX_EXEC_NUM=10`（`Config.java`，可被 `task.max.exec.num` 覆盖）三处生效：

- ES 检索 `execNum < 10`（预匹配就不捞）；
- `exec` 时 `execNum >= 10` 拒绝下发，`execNum+1` 并把 `publishtime` 推迟 10 分钟；
- `TaskDispatchThread` 扫描 `execNum>10 或 (=10 且 IDLE)` 判死。

这套"推迟等死"策略避免 exec 当场误杀，把终判交给扫描线程。

## 兜底扫描线程

- **TaskDispatchThread**（`real-scheduling/src/main/java/cn/testin/schedule/task/TaskDispatchThread.java`）：死循环（空闲 sleep 5s）`listByPending(vhost, 200)`，按 `oem_cancel_task_report` 开关分两版 SQL，捞"取消已到点 / 过期 / 匹配耗尽"的子任务交 `TaskHandlerThread` → `handleAbnormalTask`。
- **TaskDeviceCheckThread**：5 分钟周期，设备离线 SKIP。

## 已知风险与修复

1. **TMP 无兜底**：init 入库后、INIT 通知发出前宕机，TMP 永久卡住（`TaskDispatchThread` 不扫 TMP）。修复需手工处理，见 [横切-服务异常影响与数据修复](../../跨模块链路/横切-服务异常影响与数据修复.md)。
2. **通知判死**：MQ 通知失败重试 3 次推迟 10s、超 10 次且超 1 小时置 INVALID——极端故障下取消/回收通知会放弃，需人工排查 mq_info_notice 的 INVALID 记录（见 [通知处理与心跳实现](../03-实现逻辑/通知处理与心跳实现.md)）。
3. **异常设备 remove 依赖内存 map**：重启后 30s 内 `load` 未跑，remove 会假成功（见 [异常设备处理实现](../03-实现逻辑/异常设备处理实现.md)）。
