# 定时任务

> 本文是 [04-核心链路-定时任务](../04-复杂功能细节/核心链路-定时任务.md) 与 [04-核心链路-定时任务调度](../04-复杂功能细节/核心链路-定时任务调度.md) 的自然语言版（不含代码细节）。

## 功能是什么

- 定时任务让用户**按固定的周期规则（cron 表达式）自动重复创建真实任务**：配置一次，之后每到设定的时间点，平台就自动发起一次测试，不需要人工再点"执行"。典型用法是每日巡检、定时回归。
- 定时任务本身只是一份"**触发规则 + 任务参数快照**"。创建时平台会把完整的任务参数原样保存下来，每次到点就用这份快照生成一个全新的真实任务。
- **定时生成的任务与手动创建的任务完全同构**：走同一条创建、匹配、下发、执行、回收链路，产出同样的报告。对用户来说，定时任务只是"换了一种触发方式"的普通任务。
- 配置定时任务时会先创建一份模板任务，之后每次触发都基于保存的参数快照重新生成任务，并合并当时的动态信息（如当前时间、变量取值），保证每次执行用的是最新语境。

## 触发规则与约束

定时任务到点后，并不是无条件执行，而是先过一组检查，任一不满足则本次触发被跳过：

| 检查项 | 规则 | 用户可见的表现 |
|---|---|---|
| 任务状态 | 已暂停或已删除的定时任务不会被触发 | 暂停期间不会有新任务产生；暂停的任务仍可"立即执行一次" |
| 总执行次数 | 可设置累计执行次数上限，达到后不再触发 | 超限后该定时任务自动停止产生新任务 |
| 每日执行次数 | 可设置单日执行次数上限 | 当天超限后跳过，次日恢复 |
| 上次执行未结束 | 上一次触发生成的任务还没跑完时，本次触发跳过 | 防止同一定时任务的任务堆积、互相抢设备 |

每次成功触发后，平台会记录该定时任务的**累计执行次数**和**最近执行时间**，并把"定时任务 ↔ 本次生成的真实任务"建立关联——从任何一个真实任务都能追溯出"它是由哪个定时任务在哪一次触发产生的"。

## 生命周期管理

一个定时任务支持以下操作，覆盖从创建到删除的完整生命周期：

| 操作 | 效果 |
|---|---|
| 新建 | 保存触发规则与任务参数，开始按周期触发 |
| 修改 | 调整触发规则或任务参数，之后的触发按新规则执行 |
| 暂停 | 停止周期触发，但任务保留，随时可恢复 |
| 恢复 | 从暂停状态回到正常触发 |
| 立即执行一次 | 不等时间点，手动触发一次（暂停中的任务也可以用） |
| 中断 | 打断当前正在进行的本次触发 |
| 删除 | 彻底移除，之后不再触发 |
| 列表查询 | 查看名下定时任务及其执行情况（执行次数、最近执行时间） |

## 服务重启后的表现

平台服务重启不会造成定时任务丢失：

- 重启后所有仍处于"正常"或"暂停"状态的定时任务会被**自动重新注册**，继续按原规则触发；
- 重启瞬间正处于"执行中"的触发记录会被重置为"待执行"，避免出现永远卡住的执行状态。

## 注意事项

- **定时任务的参数是创建时的快照**：如果之后想改任务内容，需要修改定时任务本身，只改快照之外的配置不会反映到后续触发里。
- **触发跳过是无声的**：因次数超限或上次未结束而跳过的触发不会生成任务也不会报错，排查"为什么到点没跑"时先核对执行次数限制和上一次任务的完成情况。
- **时间规则的维护成本**：cron 表达式本身比较技术化，配置前建议先用"立即执行一次"验证任务参数是否正确，再交给周期触发。
