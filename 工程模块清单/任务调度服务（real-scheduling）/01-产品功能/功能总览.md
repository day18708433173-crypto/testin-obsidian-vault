# 功能总览

> 本页是功能维度总索引：每个功能一句话定位 + 要点 + 深入阅读。代码级链路见 [任务匹配调度实现](../03-实现逻辑/任务匹配调度实现.md)、[定时调度实现](../03-实现逻辑/定时调度实现.md)；逐 op 参数见 [接口文档索引](../07-开放接口文档/00-模块索引.md)。

## 任务接入

### 任务初始化（Task.init）
旧链路任务的唯一入库入口。app处理服务 / web/pc处理服务 把任务详情 JSON（`taskdetailJson`）发过来，本服务按"设备 × 脚本"拆分子任务/子子任务批量入库（初始状态 TMP/-1），再发 INIT 通知；初始化上报成功后激活为 IDLE(0) 并同步 ES 匹配索引。带 reqId+taskId Redis 防重锁、补测合并、任务取消即时检查、下发时间段配置。

### 任务激活（Task.execute）
把"待调度"（PENDING_SCHEDULING/-2）的子任务批量改成"待执行"（IDLE/0）。只有提测时带 `needPendingScheduling=1` 的任务需要这一步；通过 MQ `scriptExecute` 通知异步执行。

### 取消 / 回收 / 撤销
- **Task.cancel**：用户/支付平台取消任务。发 MQ `cancelTask` 通知异步处理：未开始的子任务置 CANCEL，执行中的回收，释放账号，回调测试计划。
- **Task.recover**：设备异常/掉线时回收其任务为待执行，让别的设备能重新领取。MQ `recoverTask` 异步处理。
- **Task.revoke**：撤销某台设备上的任务。带 `expirePeriod` 时先写 task_abnormal_device 表延迟撤销（由异常设备线程到点处理），否则 MQ `revokeTask` 即时撤销。

### 多端任务（cross.Task）
一次提测跨 APP/Web/PC 的"多端任务"，crossTaskid 关联各端子任务，提供跨端继续执行入口（`action=cross`）。

## 匹配下发

### APP 设备匹配（Task.match）
设备心跳触发：先 `receive` 尝试领取已预匹配的任务（Redis 里 2 分钟内的设备-任务关系），领不到再 `match` 把设备推进 Redis 匹配队列，由后台线程做 ES 预匹配。匹配成功返回任务 JSON 给设备，并做变量验证、`device_last_task_info` 记录、梆梆回调。

### Web / PC 匹配（Task.webMatch / Task.clientMatch）
与 APP 对称的两条匹配线：Web 走上位机浏览器（ucomid + 浏览器类型/版本），PC 走客户端（pcId），分别走 IWebTaskService / IClientTaskService 体系。

### 指定匹配（Task.matchTask）
恒生定制：直接指定 taskid + 设备匹配，跳过预匹配流程。deviceType 区分 1=APP / 2=WEB / 3=CLIENT。

## 执行过程

| 功能 | op | 说明 |
|---|---|---|
| 执行许可 | Task.applyForExecution | 设备跑脚本前请示调度中心：检查任务取消状态与设备并发限制，返回 确认(1)/等待(0) |
| 进度上报 | Task.processReport | 设备上报正在执行的 taskid/subtaskid/subsubtaskid，用于实时监控 |
| 预完成 | Task.precomplete | 单个脚本执行完：子子任务置"预完成"，记录输入/输出变量，有账号则释放；支持 delayperiod 推迟 |
| 结果上报 | Task.reportResult | 上传结果文件 URL：落 task_result，发 MQ 通知结果解析（RealAnalysis） |

## 运维保障

### 异常设备处理（延迟撤销）

设备被判为异常、需要撤销它上面的任务时，平台提供"**延迟撤销**"能力，而不是立刻杀任务：

- 上游把设备写进异常设备等待队列（`task_abnormal_device`），并指定**到期时间**——到期前设备若能恢复，任务不受影响；
- 后台线程到点自动触发撤销，把该设备上未完成的任务逐个收尾（结果记为"设备过期"）；
- 设备恢复后可从等待队列移除，恢复正常任务匹配。

这样设备瞬时抖动（网络闪断、临时掉线）不会误杀正在跑的任务，只有真正长期异常的设备才会被回收。代码级流程见 [异常设备处理实现](../03-实现逻辑/异常设备处理实现.md)。

### 健康检查（心跳）

任务调度服务暴露心跳探活接口，供监控探针判断服务是否存活：对 **MySQL / Redis / Elasticsearch** 三个存储各做一次轻量探测，全部通过返回成功，任一存储异常返回失败。它只验证存储连通性，不验证调度业务逻辑本身是否健康。详见 [HeartBeatController 接口文档](../07-开放接口文档/基础设施/HeartBeatController.md)。

## 定时调度

用户在 app处理服务 配置 cron 定时任务 → Quartz 到点触发 → 重新走一遍 `Task.init` 创建真实任务进入本服务。Quartz 本体在 app处理服务（real-test）侧，注册/触发/暂停/恢复的实现见 [定时调度实现](../03-实现逻辑/定时调度实现.md)；任务数据落在 db_quartz 的 quartz_job_info / quartz_job_statement，见 [存储总览](../02-技术架构/00-存储总览.md)。自然语言版说明（触发规则、次数上限、生命周期管理与重启恢复）见 [定时任务](定时任务.md)。

## 数据模型要点

任务数据在 **db_task**（表结构文档在 app处理服务 存储总览下），调度配置在 **db_quartz**：

| 表 | 角色 | 要点 |
|---|---|---|
| task_info_extra | 任务扩展（1 行/任务） | 全局参数、依赖脚本、环境配置、过期时长、自愈脚本信息、设备离线策略 |
| task_info | 子任务（核心调度表） | exec_status 状态机（-2 待调度 / -1 TMP / 0 待执行 / 1 执行中 / 2 预完成 / 3 完成 / 4 取消 / 5 跳过）、exec_num 匹配计数（上限 10）、expiretime 过期时间、allow_deviceids 可执行设备、level 优先级、publishtime 下发时间（轮次任务递推） |
| task_sub_info | 子子任务（脚本执行单元） | script_no/order_num 决定执行顺序，记录输入/输出变量 |
| task_exec_relation | 设备-任务预匹配关系 | 防重复匹配的唯一锚点，预匹配关系 2 分钟有效 |
| task_result | 结果表 | reportResult 落原始结果；异常任务（取消/过期/超限）由扫描线程补生成 |
| task_abnormal_device | 异常设备 | 延迟撤销的等待队列 |
| task_release_time_periods | 下发时间段 | 匹配查询时按时间段排除/包含任务 |
| device_last_task_info | 设备最近任务 | data 策略任务的断点续跑依据 |
| device_task_count | 设备任务计数 | 队列监控 |
| quartz_job_info / quartz_job_statement | 定时任务（db_quartz） | job_data 存完整任务 JSON；statement 记执行次数/最近执行时间，见 [db_quartz 表索引](../../数据库管理/db_quartz/00-表索引.md) |

**状态机主线**：TMP(-1) / PENDING_SCHEDULING(-2) →（INIT 上报成功 / Task.execute）→ IDLE(0) →（匹配下发）→ ING(1) →（脚本逐条预完成/完成）→ FINISH(3)；旁路：CANCEL(4) 取消、SKIP(5) 设备离线跳过。

**两条 Redis 线**：匹配队列（设备排队等预匹配）+ ES 同步队列（task_info 变更同步到 ES 匹配索引）；MQ 用 mq_info_notice 表做可靠通知（本服务消费 cancelTask / recoverTask / revokeTask / actionReport / scriptExecute / crossReport / releaseAccount / stopDeviceTask 八类，见 `real-scheduling/src/main/java/cn/testin/config/StartRunner.java`）。
