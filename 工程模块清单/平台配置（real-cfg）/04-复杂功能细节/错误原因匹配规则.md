# 错误原因匹配规则

## 主题定位

错误归因（error_cause）的匹配规则语义、共享维度、规则导出，以及配套的审计操作日志 AOP。代码级流程见 [03-错误原因规则与匹配实现](../03-实现逻辑/错误原因规则与匹配实现.md)，本文聚焦"规则怎么匹配、哪些是全局共享、有哪些坑"。

## 匹配规则语义

`error_cause_match_rule` 一条记录代表"某错误原因下的一条关键词匹配规则"：

- `rule_type`：**1 = 文本包含**（当前唯一类型），`rule_msg` 为要包含的文本；
- `status`：1 有效；
- `error_cause_type_id` + `error_cause_log_id`：分别挂到「问题类型」与「错误原因」上。

即语义是：当测试失败的日志文本**包含** `rule_msg` 时，命中对应 `error_cause_log`（错误原因），进而归类到 `error_cause_type`（问题类型）。**匹配动作在下游（app处理服务报告侧）执行**，real-cfg 只负责存规则 + 提供规则清单。

## 规则与数据维度

- 错误类型/错误原因查询固定 `(project_id = ? OR project_id = 0) AND is_delete = 0`（`ErrorCauseLogDoMapper.selectByCondition`、`ErrorCauseTypeMapper.selectErrorCauseTypeByCondition`），**project_id=0 是系统级预置项，对所有项目可见**。
- 规则全量导出 `selectAllErrorCauseMatchRule`（`GET /realcfg/error_cause_type/error_cause_match_rule`）三表 join，过滤 `log.is_delete=0 AND type.status=1 AND type.project_id=?`，按 `type.id DESC` 输出扁平 DTO——即**按 project_id 隔离导出**，跨项目共享的 project_id=0 项需单独传 0 查。

## 匹配规则的生命周期

- 新增/更新错误原因时，随 `ErrorCauseLogDTO.errorCauseMatchRules` 一起 `insertBatch`；更新带 `updateMatchRule=1` 时先 `deleteByErrorCauseLogId` 全删再重插（**全量覆盖**）。
- 删除错误原因 → 物理删其匹配规则；删除错误类型 → 级联逻辑删错误原因 + 物理删匹配规则。

## 操作日志 AOP（审计）

写操作通过 `@OperateLog(operateLog = OperateLogEnum.PROBLEM_ADD/UPDATE/DELETE)` 记审计：

- `OperateLogAspect.onLogPointcutAround` 拦截注解方法；`preOperateLog` 同步查前置数据（编辑/删除前内容），`post/exceptionOperateLog` 走 `operateLogExecutor` 线程池异步执行。
- 策略类 `ProblemAddStrategy / ProblemUpdateStrategy / ProblemDeleteStrategy` 拼 `content`（如「新增问题类型：%d %s」）与 `detailContent`（含匹配规则列表、是否误报、编辑前信息），`moduleType=-1`，经 `OperateLogStrategy.sendOperateLogToRedis` lPush 到 Redis `queue:operate_log`。
- `ProblemUpdateStrategy` 里 `id==null`（走更新接口实为新增）会改派给 `ProblemAddStrategy` 记账。
- 审计不写库、不进 `error_cause_operate_log`（那张表是任务侧上报用的，见下）。

## 任务侧操作日志（区别于审计）

`error_cause_operate_log` 是**任务执行侧上报**的归因结果（`ErrorCauseOperateLogService`），按 `task_id + sub_task_id + sub_sub_task_id + record_report_case_id` 幂等——已存在则覆盖 update，否则 insert；批量接口 `saveErrorCauseOperateLogBatch` 先批量取类型再循环落库，并把类型的 `error_report`（是否误报）透传进去。

## 坑

1. **不分页查询拿不到匹配规则**：`ErrorCauseLogService.getByCondition` 拼规则 map 时用 `getErrorCauseTypeId()` 作 key、取值时用 `getId()`，key 不一致导致 `errorCauseMatchRules` 恒为 null；分页版 `getByPageCondition` 用 `getErrorCauseLogId()` 正确。调用 `GET /realcfg/error_cause_log/condition` 时规则字段会丢。
2. **新增错误原因重名查重传参错**：`saveErrorCauseLogDo` 把 `projectId` 当作 `id` 传给 `countByErrorCauseByErrorCauseTypeId`，新增场景 SQL 误加 `AND id != projectId`，极端情况漏判重名。
3. **主键手工分配**：`saveErrorCauseType` 不依赖自增（`selectMaxId()+100`），默认「未设置问题类型」从 `USER_ERROR_MIN` 起递增，勿假设 id 连续。
